# trusted-firmware — specification

> **Status: NORMATIVE** · Scope: trusted-firmware · Last verified: 2026-10-15
> Conflicts with this document are defects. Fix them here first.

## Purpose

trusted-firmware is not a layer of the Go stack and embeds no Go layer: it is a device repository under the owner's HSM and device split, the device tier.
It owns the device firmware, the secure world and on-device key handling, and is the firmware framework and SDK for every device application: bare-metal ANSI C, AVR first, with architecture ports behind the HAL and boards as data; applications live in their own `trusted-firmware-<application>` repositories and inherit the trusted computing base, attestation, onboarding, signed OTA and the secure bootloader, and the firmware itself carries no application logic.
`sdk/go` is the Layer 0 Go SDK that drives it, with zero in-house dependencies and nothing below it to inherit or re-export; go-xkms and go-trusted-platform import it.
It provides the go-xkms backend adapter for its devices, one of the hardware crypto implementations go-quicbaas passes to go-xkms.
Its devices consume go-xkms's generic DICE and attestation verification through the adapter seam, and are provisioned and attested by go-trusted-platform.

## Boundaries

- Owns the AVR wire protocol and the firmware that speaks it.
- Owns `sdk/go` (host-sdk): Layer 0, zero in-house dependencies, no private keys; consumed by go-trusted-platform at `v0.3.0-alpha`.
- Owns the `xkms` adapter module (xkms-adapter, `github.com/jeremyhahn/trusted-firmware/xkms`) and all AVR-specific xkms code: one of the hardware crypto implementations go-quicbaas passes to go-xkms, registered through go-xkms's backend registry hook and consumed by go-quicbaas's composition; go-trusted-platform and xkey reach the devices through go-quicbaas and never import the adapter.
- Embeds no Go layer: the firmware and `sdk/go` import no project of the stack, and the `xkms` adapter module uses go-xkms only for its backend interfaces and registry hook, adding a backend and never re-exporting or re-modelling go-xkms services.
- Brings no database, cluster, engine or store of its own: device state lives on the device, and records about devices live in the deployment's one datastore, owned by the layers above.
- go-xkms holds generic DICE, EAT, device-attest-01, the verifiers, the backend interfaces and the registration hook, and nothing AVR-specific.
- go-quicbaas has a generic verifier and no firmware dependency.
- Never owns DICE ASN.1, certificate profiles, DICE verification or attestation verification: go-xkms owns them.
- Never owns device enrollment, the device registry or fleet policy: go-trusted-platform owns them.
- A gap in go-xkms or go-trusted-platform is filed against that repo, never worked around here.
- Never ports another platform before AVR has every primitive and a proven physical end-to-end run (#7); design in `docs/multi-arch/architecture.md`. The order once AVR is proven on the Nano and the Mega (#7): the SE052F, then the i.MX 95's Cortex-M7 as the cortex-m reference part, then the STM32H5 with the SE052F on its bus as the reference trusted device; the OPTIGA Trust M, RP2350, ESP32-P4 and nRF54L15 come after the SE052F and the STM32H5, with no order of work among the RP2350, ESP32-P4 and nRF54L15 yet, because the owner decides when AVR is proven. The gate is lifted for `esp32-p4`.
- Never decodes a sensor: the device offers capability, the host supplies meaning.
- Never described as "TCG DICE compliant": several DICE hardware requirements are met only procedurally on a classic AVR.

## Features

|---|---|---|---|
| wire-protocol | shipped | Frames every host–device exchange, on any transport (UART, and TCP over a WIZnet W5x00, `docs/ethernet-transport/`), CRC-16 checked, with resync. Command ids and status codes extend and never renumber. Literal golden vectors hold the C and Go codecs to the same bytes. | docs/wire-protocol/ |
| device-capabilities | shipped | Exposes GPIO, the pin scheduler, analog read, PWM, tone, pulse, EEPROM, I²C, SPI and 1-Wire as wire commands. The HAL is substituted at link time, never through a vtable. A pin told to hold a level reverts on time whether or not the host is present. There is no `delay()`. | docs/device-capabilities/ |
| boards | shipped | A board is data: a profile, pin tables and build budgets; adding one touches nothing under `src/` unless the part lacks a peripheral. ATmega328P, ATmega2560, ATmega32U4 and ATtiny85 are registered. Each board names the crypto tiers it can carry; a part with no boot section reports the none tier rather than a software tier it cannot honour. Board ids come from the board-id registry. | docs/boards/ |
| dice-attestation | shipped | The device builds its evidence: the identity from a hardware root of trust in one of the crypto tiers, the alias certificate and UCCS evidence carrying the verifier's nonce, and the device-templated PKCS#10 that proves DeviceID key possession at ACME finalize, with no signing oracle. Verifying that evidence belongs to go-xkms. | docs/dice-attestation/ |
| secure-boot | shipped | `tfw-boot` measures the application, verifies its signature, enforces the anti-rollback floor and derives the layer-0 CDI on every reset. A refusal at any step keeps the device in recovery. The build is reproducible, so the expected firmware hash is computable from source. | docs/secure-boot/ |
| device-provisioning | shipped | Takes a blank part to an identity-bearing device once, on a bench, never over the network. Provisioning commands are absent from every production image. Fuses and lock bits, the secure element and the serial are set by independent tools, none able to undo another's step. | docs/device-provisioning/ |
| host-sdk | shipped | `sdk/go` is the Layer 0 host implementation: codec, framing, transport, provisioning and attestation calls, with zero in-house dependencies. `tfwctl` and `tfwprov` are commands in that module. `tfwsim` is the real firmware built for the host, and the SDK is tested against it. | docs/host-sdk/ |
| xkms-adapter | in progress | The AVR backend for go-xkms, registered through go-xkms's backend registry hook and consumed by go-quicbaas's composition as one of the hardware crypto implementations it passes to go-xkms; go-trusted-platform and xkey reach the devices through go-quicbaas and never import it. It is a read-only key provider that answers from the device's `CAPS` reply and refuses what the part cannot do. It holds no private key and reaches the wire only through `sdk/go`. The module registers through `RegisterExternalBackend` on go-xkms v0.55.0-alpha and finalizes through `Device.AttestCSR` (#28 phases B and C). The DICE end-to-end test (`xkms/e2e/device_attest_dice_e2e_test.go`) passes in CI, in the `xkms adapter` job that runs `make xkms-test xkms-coverage`. Stays in progress: the enrollment and downstream migration work (#20, #19) and the physical-board run (#7) remain. | docs/xkms-adapter/ |
| ethernet-transport | in progress | The wire protocol over Ethernet on the AVR boards, through a WIZnet W5100 or W5500 controller on SPI, so a device reaches the network, enrols (device-attest-01, through go-trusted-platform's control plane) and attests without a serial host. The controller's hardware TCP/IP stack carries the existing frames unchanged over a TCP connection that the device opens to the control plane's device-facing endpoint. The frames, command ids and wire vectors do not change. The Ethernet link accepts only the attestation and enrolment commands. Provisioning and the device capabilities stay on the serial link, which the host SDK keeps for provisioning and tests. One driver file per controller, chosen by the board profile, runs over the HAL's SPI. No IP stack, TLS or ACME client of ours runs on the device: the ACME client is go-trusted-platform's, and the device's evidence is signed and nonce-bound end to end. The device's address, its MAC and the endpoint are configuration, taken from the board profile or from provisioned data and never hardcoded in `src/`; static addresses serve until the boot node runs DHCP, and until the shields' MAC values are supplied the MAC is a locally administered address derived from the DeviceID. The reference boards are the Arduino Nano (ATmega328P) with a W5100 shield and the Arduino Mega 2560 with the Arduino Ethernet shield. Both enrol on the element tier, the ATECC608C (MIKROE-6774 Click board) (`docs/dice-attestation/adr-possession-at-acme-finalize.md`). `sdk/go` gains a TCP transport beside serial. Seam to go-trusted-platform: its device-facing endpoint accepts these connections, and its SPEC names the same seam. | none |
| cortex-m | future | The Cortex-M architecture ports: generic, not tied to a board, Cortex-M7 and Cortex-M33 first, each a HAL and boot-HAL port. Boards are data, held in board profiles. The reference part is the i.MX 95's Cortex-M7 (row `imx95`) and the second target is the STM32H5 (row `stm32h5`). It needs ADRs for the reference part and CI emulation target (#14) and for the trust model and its relation to TF-M (#15). Until the hardware arrives, the Cortex-M targets are emulated in QEMU for CI and development. Per-architecture code lives only behind the HAL, the boot HAL and the board profiles. Starts only once AVR has every primitive and a proven physical end-to-end run (#7). | docs/multi-arch/ |
| stm32h5 | future | The second Cortex-M target, after the i.MX 95 M7: a Cortex-M33 with TrustZone, enrolling over Ethernet, on two targets. The STM32H573I-DK is the reference board: hardware crypto, ST Secure Manager and a factory device certificate. The NUCLEO-H563ZI is the secondary target: it proves our own TrustZone secure world and software crypto on a part without ST's secure services, the common case across the H5, U5 and L5 lines. One design decision is open: ST's Secure Manager as the secure world, with its PSA attestation token verified by go-xkms's EAT path, or our own TrustZone firmware. | docs/multi-arch/ |
| secure-element-se05x | future | The element tier on the NXP EdgeLock SE052F, next to the ATECC608C (MIKROE-6774 Click board) tier. The on-device C driver is ours; the host-side Go backend is go-enclave's (its row se052f-secure-element, go-enclave #191). go-xkms sees only evidence and the NXP-issued device certificate. The tier fits the ATmega2560, ATmega32U4 and Cortex-M targets, not the ATmega328P. | docs/multi-arch/ |
| optiga-trust-m | future | An element tier on the Infineon OPTIGA Trust M, the plain OPTIGA Trust M V3 shield. The on-device driver is ours; the host-side backend is go-enclave's, the same split as the SE052F. | docs/multi-arch/ |
| rp2350 | future | The RP2350 on the Raspberry Pi Pico 2 W: the firmware core as a HAL port, with DICE evidence on the part's OTP and secure boot. Enrollment goes through go-xkms into go-trusted-platform. | docs/multi-arch/ |
| nrf54l15 | future | The nRF54L15 on the nRF54L15-DK: the firmware core as a HAL port, with DICE evidence on the part's KMU and TrustZone. Enrollment goes through go-xkms into go-trusted-platform. | docs/multi-arch/ |
| mcxn947 | future | The MCXN947 on the NXP FRDM-MCXN947, a Cortex-M33 with the EdgeLock secure subsystem: the firmware core as a HAL port, with DICE evidence on the part's EdgeLock secure subsystem. Enrollment goes through go-xkms into go-trusted-platform. | docs/multi-arch/ |
| esp32 | in progress | The ESP-IDF architecture port, for the Xtensa and RISC-V ESP32 parts, the ESP32-P4 first (row `esp32-p4`, #23, implemented by #48), with an ADR for its integration boundary and transport (#16). Per-architecture code lives only behind the HAL, the boot HAL and the board profiles. | esp32-p4 | in progress | The ESP32-P4 on a PoE Ethernet board with an ESP32-C6 co-processor, the first MCU onboarded beside the Raspberry Pi nodes. The firmware core is a HAL and boot-HAL port on ESP-IDF. ESP-IDF's secure boot v2 (RSA), flash encryption, partition table and OTA are the hardware implementation behind those HALs, composed and never re-implemented. The DICE identity is keyed from an eFuse key through the HMAC peripheral, the DeviceID key is held by the DS peripheral, and no key leaves the part in the clear. The device speaks the wire protocol over Ethernet. The C6 stays off: no firmware of ours runs on it and its radio is never enabled. Per-architecture code lives only behind the HAL, the boot HAL and the board profiles, and the board takes the next free id in the ESP32 range (0x80–0xBF). The AVR gate (#7) is lifted for this row; it is tracked in #48. | docs/multi-arch/ |
| imx95 | future | The NXP i.MX 95 (FRDM-IMX95-PRO) as a board of the `cortex-m` port, with our firmware core on its Cortex-M7. The key tier is the SoC's EdgeLock secure enclave: the DICE root and keys are held there, and no key leaves it in the clear. AHAB secure boot verifies the M7 image as a signed container before it runs. The M7 reaches clocks, power and its resources through SCMI to NXP's System Manager on the M33, which stays NXP's. The M33 runs code of ours only where the System Manager leaves room. trusted-imx95 owns the platform image, its boot container and the System Manager configuration. This row owns only the M7 firmware and its board profile, with a board id in the Cortex-M range (0x40–0x7F). | docs/multi-arch/ |
| hsm-self-defence | future | HSM self-defence on the i.MX 95: the M7 application of row `imx95`, on the `cortex-m` port, enforces the tamper response, so a compromised Linux side on the A55 cannot suppress it. Its inputs are deterministic tamper signals: the EdgeLock tamper pins, AHAB and measurement failures, IMA violations, hotplug events, and loss of the heartbeat from the tamper detector on the A55. It acts through NXP's System Manager and the EdgeLock secure enclave: power domains, PHYs, key zeroisation and shutdown. A response policy signed by the tenant decides which action follows which signal, a custom response script is a signed artefact too, and the M7 accepts only a policy or script whose tenant signature verifies. The NPU model on the A55 selects among the signed policies and never acts on its own. The default response is lockdown, and keys are wiped only when a deterministic signal corroborates the model's verdict. Seam to go-xkms: the keys the M7 locks or wipes are those of go-xkms, which runs on the board as the HSM appliance, and go-xkms's SPEC names the same seam. Seam to go-trusted-platform: the signed policies and scripts reach the device through go-trusted-platform's control plane, which provisions and attests the HSM device (its `hsm-device-lifecycle` row), and go-trusted-platform's SPEC names the same seam. This row owns the M7 enforcement and the signature check. The A55 detector, the NPU model and the IMA log are outside this project, the System Manager stays NXP's, and the model work starts only after the HSM node runs. | docs/multi-arch/ |
| application-sdk | in progress | The application interface through which a device application, in its own `trusted-firmware-<application>` repository, plugs into the firmware. The application inherits the trusted computing base, remote attestation, onboarding by device profile, signed OTA and the secure bootloader, and re-implements none of them. The interface defines the application descriptor (name, version, device profile, required capabilities), the lifecycle hooks (init, run, shutdown, before-update, after-update), configuration, the application's own evidence claims carried beside the firmware's, and the OTA slots its images use. An application repository builds against a released SDK version and links one application into one image, with no dynamic loading. Applications are board-independent. An application builds for any board combination the framework supports, with the board chosen as data at build time, and no per-board application repository exists. APP_INFO (command 0x06, #51) has shipped: it reports the linked application's descriptor and runner state over the wire. The application's evidence claims have not. The firmware itself still carries no application logic. | docs/application-sdk/ |
| ota | in progress | Signed over-the-air updates of the whole image, firmware and application together, on every board with a boot section, over the network (TCP through the W5100 or W5500) and over serial. Where both transports do not fit, a board's image selects one at build time by its object list, never by `#if`; every measured image carries both. On AVR the application receives the image and stages it in an external SPI store, and `tfw-boot` verifies, copies or swaps, and evaluates it; the ATmega2560 gets A/B slots by swap-move, the ATmega328P and ATmega32U4 one internal slot with the backup in the store. The ATtiny85, with no boot section, has no OTA (proposed). Elsewhere the vendor's or community's framework is composed first: MCUboot, TF-M and PSA Firmware Update on the Cortex-M33, ESP-IDF's OTA on the ESP32-P4, AHAB on the i.MX 95 M7 (decided with #15). Every image carries trailer v1 with its board id, and `tfw-boot` refuses an image for another board; on composed platforms the trailer rides beside the vendor's signature. Every board with room verifies a signed SUIT-subset manifest (ES256, SHA-256) before activation; the ATmega328P verifies at least the trailer; the CoRIM stays the verifier's. A new image boots once on trial within a per-board timeout; the control plane confirms it after attestation, a failed trial rolls back by itself, and recovery is another OTA round. An anti-rollback floor, advanced at confirm, stops any update from lowering the security version. A new status code answers a command in the wrong OTA state. The image key and the manifest signer are go-xkms's, one hardware-backed key per board id, reached through go-quicbaas; this project and `sdk/go` hold no private key. Seam to go-trusted-platform: its device-facing OTA endpoint delivers the image and its control plane confirms after attestation (its `device-ota` seam). Seam to go-quicbaas: its reference-values store holds each image, its SUIT envelope and its CoRIM. Seam to qrdb: the RBAC permissions `ota.activate` and `ota.confirm`, tenant-scoped, in the default roles. Seam to go-xkms: its provisioning seam row, which go-xkms owns, places the verification key in the element's slot; this SPEC mirrors that row once it lands on go-xkms's main. This project keeps no registry, store or update server of its own. What runs today: tfw-boot's trailer gate and its one trial boot. The manifest gate is built but nothing calls it yet. On the external store (#75), the application stages an image and tfw-boot checks it again and copies it in. The copy is a `BOOT_STORE` row on the 2560 without OTA in boot, and it does not fit the 4 KB parts. Not yet: the A/B swap-move, the ATmega328P and ATmega32U4 restore, and `OTA_CONFIRM` and `OTA_ACTIVATE` on the wire (`docs/ota/architecture.md`). | docs/ota/ |
| device-onboarding | future | The seam through which a DICE-only device (no TPM) enrolls into the go-trusted-platform control plane by device profile. The device presents its DICE evidence: the alias chain and UCCS claims, including the firmware and application measurements. go-quicbaas composes and re-exports go-xkms's generic DICE verification, with this project's xkms adapter as one of its hardware implementations, and that verification checks the evidence. go-trusted-platform reaches the device through go-quicbaas, never imports the adapter, and matches the device to its profile and records it. This project supplies the evidence and the adapter and owns no enrollment, registry, profile or verification. go-trusted-platform's, go-quicbaas's and go-xkms's SPECs name the same seam. | docs/xkms-adapter/ |

- Wire protocol: the framed binary protocol, transport-independent (UART, TCP over W5x00) — [wire-protocol/api.md](wire-protocol/api.md).

- Go SDK: `sdk/go` (host-sdk), consumed by go-trusted-platform at `v0.3.0-alpha` — [host-sdk/api.md](host-sdk/api.md).

- Build, test and flash: the Makefile targets — [development/building.md](development/building.md).

## Release criteria

- Dev complete: `docs/SPEC.md` and `ROADMAP.md` exist in the handbook's shapes and agree (#39).
- Dev complete: the owner approves the whole of both files.
- Dev complete: CI conforms to the handbook's `software/conventions/ci-standard.md`: build, unit tests, integration tests, security scans and the latest-version check, all in the project's devcontainer image.
- Dev complete: this project's own rows shipped, and every row go-trusted-platform's SPEC names on it as a seam shipped (its `firmware`, `avr-attestation` and `device-enrollment` rows), with the `sdk/go` and `xkms` adapter APIs stable; until then tags are `-alpha` only.
- Dev complete, AVR: the Arduino Nano (ATmega328P) and the Arduino Mega 2560 each enrol (device-attest-01) and attest over Ethernet against the test control plane, and the firmware's tests pass on both boards; the ATmega32U4 and the ATtiny85 are covered by the simulator. Every test except the element tier on the ATECC608C (MIKROE-6774 Click board) and ACME enrolment runs on both boards now; the element tier and device-attest-01 enrolment run on both boards the day the ATECC608C (MIKROE-6774 Click board) arrives.
