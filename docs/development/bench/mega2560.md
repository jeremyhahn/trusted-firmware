# Bench board: Arduino Mega 2560

The factory record for the bench Mega, written before the project's first
write to it under the owner's ruling of 2026-10-16 (CA m346): every bench board
is the project's to flash, provision and reconfigure, once its factory
bootloader and fuse bytes are on its page. The restore procedure puts them
back when the board is finished with.

| | |
|---|---|
| Board | Arduino Mega 2560, USB through the on-board 16U2 (`2341:0042`), `/dev/ttyACM0` on the bench host |
| MCU | ATmega2560, 256 KB flash, 4 KB EEPROM, 8 KB SRAM, 16 MHz |
| Programmer | USBasp clone (`16c0:05dc`) on the Mega's ICSP header ([the USBasp path](../isp-route.md#the-usbasp-path-taken-owner-2026-10-15)) |
| Toolchain | Debian 13 `avrdude` 7.1, `avr-gcc` 14.2.0, the package hashes in [the ISP route](../isp-route.md#toolchain-and-sources) |

## Factory values

| | Value | Where it came from |
|---|---|---|
| Signature | `0x1E9801` | ISP, 2026-10-16 (both reads below) |
| Low fuse | `0xFF` | the same |
| High fuse | `0xD8` | the same |
| Extended fuse | `0xFD` | the same |
| Lock | `0xCF` | the same |
| Boot section, `0x3E000`–`0x3FFFF` | Arduino's `stk500boot_v2_mega2560.hex` | read 2026-10-16, see below |

The fuse bytes are the factory ones. The first ISP read on 2026-10-16
([the Mega, 2026-10-16](../isp-route.md#the-mega-2026-10-16)) and the Company
Agent's own reading agree on all five, and the read for this page gave the same
bytes again. Nothing on the bench has written a fuse or a lock bit.

The boot section is not untouched since the factory. An Arduino IDE "Burn
Bootloader" over the USBasp rewrote it on 2026-10-16 (CA m233, recorded in [the
re-provisioning](../isp-route.md#the-mega-re-provisioned-over-isp-2026-10-16)).
What it holds now is the stock image, byte for byte: see the identity below.

Decoded against the ATmega2560 data sheet (Memory Programming, the fuse byte
tables; a fuse bit is programmed when it reads 0):

| Byte | Bits | Meaning |
|---|---|---|
| High `0xD8` | `OCDEN` 1, `JTAGEN` 1, `SPIEN` 0, `WDTON` 1, `EESAVE` 1, `BOOTSZ1:0` 00, `BOOTRST` 0 | JTAG and on-chip debug off, ISP on, `EESAVE` **unprogrammed**, 4096-word (8 KB) boot section at `0x3E000`, reset enters it |
| Low `0xFF` | `CKDIV8` 1, `CKOUT` 1, `SUT1:0` 11, `CKSEL3:0` 1111 | full-swing crystal, no clock divide, slowly rising power |
| Extended `0xFD` | `BODLEVEL2:0` 101 | brown-out at 2.7 V |
| Lock `0xCF` | `BLB1` 00, `BLB0` 11, `LB` 11 | `BLB1` mode 3: SPM may not write the boot section and (E)LPM from the application may not read it; no other restriction (data sheet §29.4, Table 29-3) |

### The bootloader's identity

The 8 KB section holds 7454 bytes of code and data at `0x3E000`–`0x3FD1D`. Its
strings name it: `Arduino explorer stk500V2 by MLS`, `ATmega2560`, and the
build date `Mar  7 2013`. Its vector table begins `0d 94 89 f1 0d 94 b2 f1`.

It is Arduino's prebuilt `bootloaders/stk500v2/stk500boot_v2_mega2560.hex`
from [ArduinoCore-avr](https://github.com/arduino/ArduinoCore-avr/blob/master/bootloaders/stk500v2/stk500boot_v2_mega2560.hex),
the file the IDE's "Burn Bootloader" writes for the Mega 2560. Loaded into an
`0xFF`-filled 8 KB section, it equals the section read off the board, all
8192 bytes.

| File | SHA-256 |
|---|---|
| `stk500boot_v2_mega2560.hex` at ArduinoCore-avr `master` and at tag `1.8.6` (the same file) | `081bd53f385df747b03bdafe7e154c1f72589f490be8138f3c4cc5517c93253b` |
| Its image in the 8 KB section | `fdef04c5…742db711`, the board's |

Debian's `arduino-core-avr` 1.8.7+dfsg-1~deb13u1 is **not** that file. The
package rebuilds the bootloader from `stk500boot.c` (its strings carry the
build date `Mar  4 2026`), so its hex (SHA-256 `48594ee2…c663f00`, 6030 bytes)
differs from the board's in 7120 of the 8192 bytes. Use Arduino's file, not
Debian's, to put the stock bootloader back.

The source's licence is GPL-2.0-or-later (`stk500boot.c`, Peter Fleury and
others; `License.txt` beside it is the GPL v2). This repository is
AGPL-3.0-or-later and commercial, and the commercial licence cannot cover GPL
code, so the hex is not committed. The restore target takes its path.

### The USBasp cannot see the low 128 KB

Over ISP, `0x00000`–`0x1FFFF` read back as a copy of `0x20000`–`0x3FFFF`. The
application region read all `0xFF` up to `0x1E000`, then held the bootloader
again at `0x1E000`–`0x1FD1D`. The application was there all along: it answered
`caps`, and the stock bootloader read it at `0x00000`–`0x0447B` over serial.

So this USBasp addresses only the upper half of the ATmega2560's flash. The
likely cause is firmware older than the long-address request avrdude sends for
parts over 128 KB; the same old firmware is why every run prints `cannot set
sck period`. That is inferred, not read off the programmer. The boot
section is in the upper half, and its ISP read equals the serial read. Two
things follow:

- **ISP reads and writes below `0x20000` are not to be trusted with this
  programmer.** The 2026-10-16 note "over ISP, flash reads `0xFF` from
  `0x00000`" ([the Mega, 2026-10-16](../isp-route.md#the-mega-2026-10-16)) is
  this effect. That the application had been erased then rests on the stock
  bootloader's read, not the ISP's.
- An application written over ISP with this programmer
  ([secure boot](../secure-boot/user.md#install-the-application-under-tfw-boot),
  the ISP route) would not land at `0x00000`. A USBasp firmware update, or
  another ISP programmer, comes first.

and [the bench record](#bench-record-2026-10-18)). The part holds `0xD8`, the
factory value: `EESAVE` is unprogrammed, so a chip erase erases the EEPROM.

its read-back survives. An ISP read on 2026-10-18 to confirm `0xD8` is pending;
it needs the USBasp on the bench host.

Both EEPROM hashes are the factory record's. After the write the `CRYPTO=soft`
application still answered `tfwctl /dev/ttyACM0 ping` and `caps`, which reported
the same board, protocol and root of trust as before.

**tfw-boot was not flashed.** Every 2560 row in `BOOT_SUPPORTED` is
`atecc608a`, so it needs the element on the I²C bus, and the ATECC608C on the
MIKROE-6774 did not answer: no ACK at `0x35` (TNGTLS) or `0x38` (TMNGTLS) after a
wake. `0x36`, the TFLXTLS default, is the address the soft image keeps for the
platform. With no element there is no row, so `make boot-flash` was not run.
Two more things stand in the way after the element:

- tfw-boot verifies a signed application, and this tree has no signing key.
- [The USBasp cannot see the low 128 KB](#the-usbasp-cannot-see-the-low-128-kb),
  so the application could not be written over ISP to `0x00000`.

## Restore

```sh
make board-restore BOARD=atmega2560 BOARD_RESTORE_HEX=<path>/stk500boot_v2_mega2560.hex
```

| | |
|---|---|
| Hex | Arduino's [`stk500boot_v2_mega2560.hex`](https://github.com/arduino/ArduinoCore-avr/blob/master/bootloaders/stk500v2/stk500boot_v2_mega2560.hex), SHA-256 `081bd53f385df747b03bdafe7e154c1f72589f490be8138f3c4cc5517c93253b` (not Debian's, above) |
| Fuses written | low `0xFF`, extended `0xFD`, high `0xD8`, then lock `0xCF` |
| Values from | `FACTORY_*` in `boards/atmega2560/profile.mk` |

The target refuses any other hex. The flash write erases the chip, so it goes
through `boot-flash`'s `EESAVE` guard: with `EESAVE` programmed it writes; with
it unprogrammed it refuses unless `BOOT_EEPROM_RESTORE=1`, which saves the
EEPROM, writes, puts it back and compares. The high fuse goes back to `0xD8`,
`EESAVE` unprogrammed, as the factory had it; the lock byte is written last,
since the erase cleared it. All four bytes are read back and compared.

The bootloader is written over the USBasp, and it sits in the upper 128 KB this
programmer reaches. The application region is erased and not put back: the
board leaves with the stock bootloader and no sketch, as a new board does.

(#223: the AUTH fail-open fix, OTA #205, robustness #222, the xkms adapter
#194), train land2 (#224: device provisioning #197), #214, #215 and #225
merged. The board has no Ethernet shield on it now, so this is the serial half
only. The toolchain is [the probe's](../wiznet-probe.md#toolchain), unpacked
under the lane's home directory. Nothing went over ISP. No fuse, lock or
boot-section byte was read or written, no chip erase was sent, and both flashes
went through the stock bootloader with `-D`. Still no SPI NOR part on D8.
