# Bench board: Raspberry Pi Pico 2 W (RP2350)

The factory record for Pico 2 W #1, read before the project's first write to
it. Owner ruling 697 lifts the SPEC AVR gate (#7) for the RP2350 and orders
the HIL boot and feature check on the board; the device rules are CA
581/582/583 and ruling 225(2): the factory state is recorded first, the OTP is
read and never written, and the only writes are `picotool load` of a bring-up
image into flash and `picotool reboot`.

| | |
|---|---|
| Board | Raspberry Pi Pico 2 W #1, USB on the bench host, in BOOTSEL mode as found (`2e8a:000f`, "RP2350 Boot") |
| MCU | RP2350A (QFN60), revision A2, two Cortex-M33 cores (and two Hazard3), 520 KiB SRAM, 4 MiB QSPI flash |
| Programmer | none: picotool over the boot ROM's USB PICOBOOT interface (the board has no debug probe) |
| Toolchain | picotool v2.1.1 built from source against pico-sdk 2.1.1 (`picotool version`: `picotool v2.1.1 (Linux, GNU-14.2.0, Release)`); `arm-none-eabi-gcc` 14.2.1 (Debian 15:14.2.rel1-1) |

The chip id is a serial and stays in the bench host's record only.

### OTP

`picotool otp dump` reads all 4096 rows (raw 24-bit values). 23 rows are
non-zero, all factory-programmed; named after the RP2350 datasheet's OTP data
map:

| Rows | What they are | State |
|---|---|---|
| `0x000`–`0x00b` | `CHIPID0`–`3` and `RANDID0`–`7`: the chip id and the factory random id | set (per-chip, not copied here) |
| `0x010`, `0x011` | `ROSC_CALIB`, `LPOSC_CALIB` | set |
| `0x018` | `NUM_GPIOS` (30 GPIOs, the QFN60 part) | set |
| `0x036`, `0x037` | `INFO_CRC0`, `INFO_CRC1` | set |
| `0x040`–`0x07f` | `CRIT0`, `CRIT1` (secure boot, debug disable, glitch detector), `BOOT_FLAGS0/1`, `BOOTKEY*` and the rest of the boot configuration | **all zero**: secure boot off, no boot key, glitch detector off |
| `0xf80`, `0xf81`, `0xf83`, `0xf85`, `0xffd`, `0xfff` | page lock rows of pages 0, 1, 2, 61 and 63 | the factory page locks |

Every other row reads zero. Nothing on the bench has written an OTP row, a
page lock or any boot, key or glitch-detector bit, and no lane does
(`picotool otp set/load/permissions` and `seal` are never run).

### Flash

`picotool save` of the whole 4 MiB from the XIP base. The flash is not blank:
268 122 bytes are not `0xFF`, with no picotool binary info in them (the
"Program Information: none" above), so whatever it holds came without an SDK
binary-info block.

### The repository's picotool path does not run with picotool 2.1.1

`make board-record BOARD=rp2350-pico2w CM_PROBE_SERIAL=<serial>` wrote the
OTP dump (identical to the one above) and then failed on the flash read:

```
    picotool save -r <from> <to> [-v] [--family <family_id>] [device-selection]
make: *** [mk/board-restore.mk:66: board-record] Error 1
```

`cm_read_picotool` and `cm_write_picotool` in `mk/arch/cortex-m.mk` put
`--ser <serial>` before `-r` (and before the file of `load`); picotool takes
the device selection after the file. `scripts/test_cortex_m_flash.py` runs the
recipes against a fake tool, which accepts that order. With no record from
`board-record`, `make flash` and `make boot-flash` refuse too. Not fixed here
(this lane changes no mk); the same operations were run by hand with the
device selection last:

```sh
picotool load -v tfw-boot.bin -t bin -o 0x10000000 --ser <serial>
picotool load -v trusted-firmware.bin -t bin -o 0x10008000 --ser <serial>
picotool info -a --ser <serial>
picotool otp dump --ser <serial> > otp-after.txt
picotool reboot --ser <serial>
```

Both loads ended `Verifying Flash: [====] 100%` and `OK`. Each erases only
the sectors it covers; the factory bytes past the application stay.

### What the boot ROM saw

`picotool info -a` after the loads, still in BOOTSEL:

```
Program Information
 target chip:            RP2350
 image type:             ARM Secure

Metadata Block 1
 address:                0x10000180
 next block address:     0x10000180
 block type:             image def
 target chip:            RP2350
 image type:             ARM Secure
 ...
 secure boot:            0
 flash size:             4096K
```

The boot ROM finds tfw-boot's IMAGE_DEF at `0x10000180`, a single block
looping to itself, Arm Secure. `flash size: 4096K` settles the board page's
question: the part is 4 MiB, so the platform block at `0x103FF000` does not
alias.

The OTP dump after the writes is byte-identical to the factory dump:
SHA-256 `e68dd45f6795032e6ae043bb1900a45b29d1402254653068398f8cb5f5394353`
both times (`cmp` reports no difference).

### The boot check

The repository's boot check for a Cortex-M board is `make hw-test BOARD=<board>
PORT=<dev>`, the `TestFirmware*` rows over the board's console. The Pico 2 W's
console is UART0 on GPIO0/GPIO1 (header pins 1 and 2), and **nothing is wired
to the board's pins**: no USB-to-UART adapter, no external part. `hw-test`
has no port to open, so it was not run.

What could be checked over USB alone: after `picotool reboot` the board left
BOOTSEL and did not come back on USB. No `2e8a` device was on the bus at any
of six reads, 2 s apart, after the reboot (07:39:28Z), and no new USB node
appeared. The RP2350 boot ROM drops to USB BOOTSEL when it finds no bootable
image, so the board not coming back means the ROM accepted the IMAGE_DEF and
entered tfw-boot. Whether tfw-boot then verified and entered the application
cannot be seen without the console.

| Check | Result |
|---|---|
| Write and read back, both images | pass (`picotool load -v`) |
| Boot ROM parses the IMAGE_DEF | pass (`picotool info -a`, above) |
| Boot ROM launches the image after reboot | pass (no BOOTSEL fallback on USB) |
| tfw-boot to application handoff, `hw-test` rows | **not run**: no console wired to UART0 |
| OTP unchanged | pass (identical dump before and after) |

## HIL feature check: not run on the board

The feature image is main 8bf3cee1 with every rp2350 firmware row on:

```sh
make BOARD=rp2350-pico2w I2C=1 PERIPH=1 \
     build/rp2350-pico2w/soft-i2c-analog-pwm-tone-eeprom/trusted-firmware.hex
```

| Image | Size | SHA-256 |
|---|---|---|
| `build/rp2350-pico2w/soft-i2c-analog-pwm-tone-eeprom/trusted-firmware.elf` | | `f8de461723aaa0a29d1735de2126bcdf9947c45951a1dbe8cc149afd5062914e` |
| the same, binary | 13 676 bytes | `b4a4ed1f288187849764fa614b84127b0bba9a2036308774b646eeae84fc61ca` |

It was built, not written. Three things stop the check on the board:

1. Every feature (I2C, PWM, ADC, tone, flash EEPROM) is exercised through
   `tfwctl` over the console, and nothing is wired to UART0.
2. The board now runs the default image and has no USB stack, so picotool
   cannot reach it. It returns to BOOTSEL only with the BOOTSEL button held
   while USB is replugged, which is a hand at the bench.
3. On main, `make flash` refuses the `I2C=1 PERIPH=1` row
   (`CM_FLASH_GATED_WHY` in boards/rp2350-pico2w/profile.mk) until the
   gate-lift lane (`row/429-rp2350-gate-lift`) lands ruling 697.

| Feature | Result | Expected until |
|---|---|---|
| I2C (I2C0, GPIO4/5) | not run | console wired. The foreign-STOP Codex P1 is the gate-lift PR's |
| PWM | not run | console wired |
| ADC (analog read, adc-ref) | not run | console wired. The pin-restore Codex P1 is the gate-lift PR's |
| Tone (TIMER1 alarm) | not run | console wired. The alarm-retry Codex P1 is the gate-lift PR's |
| Flash EEPROM (user sector) | not run | console wired |

To run it: a 3.3 V USB-to-UART adapter on GPIO0 (TX), GPIO1 (RX) and GND;
the board put in BOOTSEL by hand; the feature image written as above after
the gate-lift PR lands; then `make hw-test BOARD=rp2350-pico2w PORT=<adapter>`.
With nothing on the I2C, ADC, PWM or tone pins, the I2C rows can only show
the no-device (NACK) path and the ADC rows a floating pin.

## State left on the board

Pico 2 W #1 runs main 8bf3cee1's default image: tfw-boot at `0x10000000`,
the application at `0x10008000`, the factory bytes beyond. OTP as it came.

## Restore

Put the board in BOOTSEL by hand (hold BOOTSEL, replug USB), then
`picotool load -v flash-factory.bin -t bin -o 0x10000000 --ser <serial>` and
`picotool reboot --ser <serial>` put the flash back as it came. The OTP was
never written, so there is nothing else to restore.
