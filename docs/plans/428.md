# Plan: row `imx95` (#428)

## Objective

Ship SPEC row `imx95` as one row PR on `row/428-imx95`: the NXP i.MX 95
(FRDM-IMX95-PRO) as a `cortex-m` board, with our firmware core on its
Cortex-M7 (`boards/frdm-imx95-m7`, provisional id 0x41).

Each fold is one `git merge --no-ff` commit; conflicts keep both sides.
After each conflicted fold, `make host-test` runs before the next.

## Follow-on (PR #449): our Cortex-M7 image on the board, console read

Objective: load the project's frdm-imx95 Cortex-M7 image into RAM only and
capture its console output on the M7 UART; record commands and output in
docs/development/bench/frdm-imx95.md.

1. Board state record before any load (bench doc, M7 load section).
2. Build the M7 image with the frdm-imx95 board target from mk/.
3. Load into RAM: remoteproc if Linux controls LM1; otherwise the SM
   monitor (`lm` shutdown/boot of LM1) with the image placed in M7 TCM.
   No eMMC write, no saveenv, no fuse, no ELE/ahab command, no break.
4. Capture the M7 console; record it. Fix the source file a failing step
   names, with its host test.
5. make host-test, make lint, make ci; PR labelled code-review, task:ready.

Result of step 3: blocked. The SM configuration (mSel 0) gives no RAM-only
route: remoteproc only attaches, TRDC blocks the A55 from the TCM, the SM
monitor reaches no memory and sets no vector. Steps 3 and 4 wait for an
owner decision: an M7 image in the boot container, mSel 1, or a
serial-download boot.

Scope change. Step 3's RAM-only load and its "no eMMC write" are replaced
by ruling 644 (1), verbatim:

> (1) #449 i.MX95 M7, decided: the board is a dev board with full write access (owner 10-16). Load the M7 image the non-volatile way. Read and back up the current boot container (imx-boot) from the boot device first, keeping the backup in the bench record. Then build an imx-boot that carries our M7 image for LM1, write it from the A55 Linux to the boot device, reboot, and capture the M7 console (port 2). The recovery path is restoring the backup, or uuu over USB serial download if the board fails to boot, which needs the owner to set SW4; say so before writing. Never send a serial break.

So this row carries `boards/frdm-imx95-m7/imx-boot-m7.py`, which replaces
only the M7 entry of the board's own imx-boot. The rest of the container,
and building it from source, stay with trusted-imx95 (docs/SPEC.md).

6. Back up the eMMC boot container (offset 0x8000) from the A55 Linux;
   digest on board and bench host match, recorded in the bench doc.
7. Build an unsigned imx-boot with only the M7 image replaced (same ELE,
   OEI, SM mSel 0, TF-A, U-Boot); recipe under `boards/frdm-imx95-m7/`.
8. Write it at the same offset, read back, digest match; `reboot`; capture
   the M7 console (port 2) for our banner. Recovery: restore the backup;
   if the board does not boot, uuu over USB serial download (owner sets SW4).

Result of 6 to 8: backed up, built, written and read back; after an SM
`reset` the board boots from it and the M7 runs our image (linked at ITCM
0, the SM's M7 vector; a Linux `reboot` resets the A55 LM only). Port 2
stays silent: the M7 must mux its LPUART3 pads (GPIO_IO14/15) over SCMI pin
control, and our image has no SCMI channel yet.

9. Firmware slice (no board): the M7's SCMI channel in board_profile.h,
   CRC-32 in the SMT transport, `console_pins.c` muxing GPIO_IO14/15 (SM
   pins 18/19, ALT1) before LPUART3 starts. Test: `test_imx95_console_pins`
   (layout, order, CRC both ways, refusal), `test_imx95_hal` (asked first).
10. Device slice: rebuild, write, SM `reset`, port 2 shows our boot frame
    (bench doc, section "Next slice"). Then pad config, RX daisy, NVIC 64.
    Result: pads ALT1, LPUART3 clocked, one 0x00 on port 2, no frame.
11. Firmware slice (no board): the M7 path from `tfw_hal_uart_init` to the
    first frame. BAUD at 24 MHz pinned (`test_imx95_soc_calc`, 115200 is
    x26 by 8), `.faultframe` placed before `.resetmark` in image.ld (the
    "dot moved backwards" warning), LPUART3 transmit pumped from the main
    loop's polls as well as IRQ 64 (`test_imx95_hal`: sent without the
    interrupt); bench record section 8 lists what port 2 must show.
12. Fix slice for the Codex review (no board). The SCMI pin-control encoder
    refuses configs past its 32-byte payload (maximum 2, derived), with a
    boundary test in `test_imx95_console_pins`, which joins host-test
    (HOST_EXTRA_BINS). `IMX_BOOT=1` in profile.mk links the container's
    image at ITCM 0. `imx-boot-m7.py` takes the ELF and refuses one not
    loaded at the container's M7 address, or whose reset target is outside
    its bytes. The next device run writes the relinked image (bench record,
    "Next slice").
13. Device run of steps 11 and 12 (bench record section 9). The container
    check passed and the image booted from the eMMC. Port 2 is unchanged:
    one 0x00, no frame. The DTCM reads were refused (TRDC: no A55 access
    through MRC2), so section 8's last three rows stay open. Next: an owner
    decision on a read path (debugger, or SM TRDC access), or step marks
    written straight to LPUART3 DATA through `startup()`.
14. Step marks (DS-8876): a bench-only build setting (off in release
    images, removed in step 21) sent one raw byte per stage on LPUART3 by polling DATA: R at
    reset entry, D after .data/.bss, M before main, P after the pad request
    (then r, d, m again, as the earlier ones may be lost before the pads are
    routed), U after `tfw_hal_uart_init`, with a host test and a board row

    section 10. Result: no mark at all, so port 2 cannot tell
    whether the M7 runs the reset handler or whether LPUART3's writes never
    reach the line. No further write. Next is the owner's call: an M7
    debugger, SM TCM read access for the A55, or LPUART3's M7 address

15. Fix slice for the second Codex review (no board). The transmit retry
    pumps the ring before it reports full, so a full ring drains without
    the interrupt (`test_imx95_hal`: a full ring drains without it).
    `IMX_BOOT` names its own build directory, so changing it relinks.

16. Step-mark diagnosis (DS-8879). The step-mark build named its own build
    directory (`-steps`), so the marks are never lost to objects compiled
    without them. On the board, read-only first: LPUART3's address in the
    A55 device tree against 0x42570000, the SM's M7 CPU and LM1 state, and

    and capture port 2. Bench record section 11. Result: a clean rebuild
    reproduces the board's container byte for byte and stores `R` to
    LPUART3 DATA first, so no new image. The device tree agrees on
    0x42570000. The M7 is in RUN and LM1 is on. LPUART3 sits behind TRDC
    MBC0, and neither the A55 nor the SM monitor can read it. Next: the
