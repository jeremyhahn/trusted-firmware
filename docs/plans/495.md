# Plan: #495 RP2350 OTA_CONFIRM request to tfw-boot

## Objective

On the RP2350 the platform block is QSPI flash behind XIP, so the plain store
`src/hal/cortex-m/rp2350/hal_eeprom.c` makes for the confirm request at
`TFW_BOOT_CONFIRM_ADDR` writes nothing on the part, and tfw-boot
(`boot/boot_swap.c`, `tfw_boot_nvm_read`) never sees the request: a trial
image cannot be confirmed. This row routes that write through tfw-boot's flash
helper (`tfw_rp_flash_update`) into the platform sector, as the user span's
writes already go. Remaining slice 1 of `docs/boards/rp2350-pico2w.md`
(audit #480).

## Slices

1. **Confirm request through the flash helper** (no hardware).
   - `hal_eeprom.c`: a write of `TFW_BOOT_CONFIRM_LEN` bytes at
     `TFW_BOOT_CONFIRM_ADDR` is a read-modify-write of the platform sector
     through `tfw_rp_flash_update`, interrupts masked and the masked time
     credited as for the user sector, then read back through XIP; a
     mismatch is `TFW_ERR_INTERNAL`. Every other write below
     `TFW_BOOT_EE_LEN` stays `TFW_ERR_RANGE`.
   - `test/unit/test_rp2350_eeprom.c`: a new case writes the request and
     reads it back from the NOR model's platform sector, with one erase
     recorded at the platform sector's offset and the sector's other bytes
     kept; a second case shows a corrupted read-back is
     `TFW_ERR_INTERNAL`. The existing boot-area case now expects the one
     platform erase.
   - `changelog.d/495-rp2350-confirm.md`.

## Tests

`make unit-test` (the rp2350 EEPROM test over the NOR model); `make firmware`
for the rp2350 board still builds.
