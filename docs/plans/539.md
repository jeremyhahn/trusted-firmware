# #539: ESP32-P4 Ethernet DHCP lease and tfw-wire over TCP in the feature matrix

## Objective

Ruling 768: every built-not-run row on the ESP32-P4 carries a dated hardware
result. The Ethernet link is in the matrix of `docs/boards/esp32p4-poe.md`;
the DHCP lease and tfw-wire over TCP from the bench host have no row of their
own. Add both, each with a dated pass or a dated failure naming its cause.

## Slices

1. This plan.
2. The two rows, run on the board as flashed (no flash write):
   - **Ethernet DHCP lease**: the lease line on the USB console (read only,
     no reset, no serial break), and the board answering `ping` from the
     bench host at the leased address.
   - **tfw-wire over TCP**: `make hw-test BOARD=esp32p4-poe
     PORT=tcp:<board>:21574 HW_TEST_RUN='^TestFirmwareCaps$'` passes
     (the brief's `HW_TEST_RUN='CAPS'` matches no test: `no tests to run`).
   Rows go in the matrix with the date and the evidence; a changelog.d entry.

3. Slice 2, boot console: the first run read the console without a reset
   and saw only stale fragments. Capture the boot instead:
   - start a capture on the USB console (pyserial, 115200, 30 s to a file
     outside the tree);
   - reset the chip through the USB-serial reset line, as esptool's
     `hard_reset` does (RTS/DTR toggle; no serial break, no flash write);
   - a lease line (`got ip` from the DHCP client) gives a dated pass; a
     static-address line gives a dated "static overlay on the running image",
     next step an image built without the overlay (ESP-IDF, outside the
     lane image);
   - then `make hw-test BOARD=esp32p4-poe PORT=tcp:<board>:21574
     HW_TEST_RUN='^TestFirmwareCaps$'` confirms the wire still answers.
   Result 2026-11-17: no lease line; the got-IP gateway is the overlay's
   documentation-range placeholder, so the row reads "static overlay".
   The image logs no line naming the path that set the address.

4. Slice 3, image without the static overlay (ruling 768 wants the lease):
   - ESP-IDF v5.5.5 outside the clone, as #552 step 1 (`git clone -b v5.5.5
     --recursive`, `install.sh esp32p4`, then `export.sh`);
   - `make esp32-build BOARD=esp32p4-poe
     ESP_SDKCONFIG_EXTRA=boards/esp32p4-poe/sdkconfig.hil0`: the board's
     defaults leave `CONFIG_TFW_ETH_STATIC_IP` unset, so the DHCP client runs;
   - save the running app partition (`esptool read-flash` of the app slot,
     outside the tree) as the restore image, then `esptool write-flash` of the
     sealed app at the app offset only: no bootloader, table, data-partition
     or eFuse write, no erase;
   - capture 30 s of boot console across an RTS reset, as slice 2;
   - `make hw-test BOARD=esp32p4-poe PORT=tcp:<leased address>:21574
     HW_TEST_RUN='^TestFirmwareCaps$'`.
   If the board's bootloader or layer-0 check refuses the new app (the build
   makes its own image key), write the saved app image back and record the
   cause as the row's dated failure.

No test code changes: both rows use existing targets and tests.

## Out of scope

- Any flash write (if one is needed: app partition only), eFuse writes,
  whole-chip erase.
- The board-dials rows (`HW_ETH`), which need the host on the dev VLAN.
- Recording the address, MAC, host names or device paths in the tree: the
  file says `PORT=tcp:<board>:21574` and "MAC recorded in the bench record".
