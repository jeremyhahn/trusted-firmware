# #544: STM32H573I-DK hardware crypto (PKA ECDSA P-256, HASH SHA-256)

## Objective

Give the STM32H573I-DK a hardware tier beside its soft one (ruling 768): SHA-256
on the HASH peripheral and ECDSA P-256 sign/verify on the PKA, behind
`include/tfw/crypto.h`, selected by the board profile. TrustZone, the Secure
Manager and the factory certificate stay owner-gated (CA 583). The keys stay
where the soft tier keeps them, so CAPS still reports `TFW_CRYPTO_SOFTWARE`:
the peripherals speed the arithmetic, they do not protect a key.

**Not confirmed** (RM0481 not read): whether the PKA reaches INITOK with only
the RNG's bus clock on, and the HASH's timing. Each driver polls with a bound;
a peripheral that does not answer makes the provider answer from the soft code
for the rest of the boot, so an unconfirmed fact costs speed, never a result.

## Slices

1. **Plan** (this file).
2. **HASH SHA-256**: `src/crypto/stm32h5/h5_hash.c` (`tfw_h5_hash_sha256`),
   register access through `h5_crypto_regs.h` so the host links a model.
   Test `test/unit/test_h5_hash.c`: a model of the HASH that rebuilds the
   message from DIN and STR.NBLW and digests it with `src/crypto/sha256.c`;
   the FIPS 180-2 vectors (empty, "abc", the 448-bit one, a 1000-byte run and
   every length 0..67), a timeout that reports `TFW_ERR_TIMEOUT`.
3. **PKA ECDSA P-256**: `src/crypto/stm32h5/h5_pka.c` (sign and verify), the
   RAM layout and result codes above. Test: a model that checks the operand
   layout (word order, the two-word terminator, the bit counts) and answers
   the verify with micro-ecc; the soft provider's vectors.
4. **Provider and profile**: `src/crypto/stm32h5/provider.c` wraps the soft
   provider (renamed per object, as the auto tier does) and routes `sha256`,
   `sign`, `verify_operator` and `verify_image` to the drivers, falling back to
   soft on a peripheral that does not answer. `boards/stm32h573i-dk/profile.mk`
   names the tier (`BOARD_TIERS := soft stm32h5`); the soft images unchanged.
5. **Hardware check** on the kit (ruling 768): build
   `make docker-firmware BOARD=stm32h573i-dk CRYPTO=stm32h5`, flash the
   application region with the board page's pyOCD route (flash program only, no
   option bytes, RDP, TZEN, OTP, WRP or mass erase), run
   `make hw-test BOARD=stm32h573i-dk` on the crypto rows (hash, verify, CAPS),
   and record each row's dated result in `docs/boards/stm32h573i-dk.md`. A driver
   defect found is fixed in `src/crypto/stm32h5/` with a host test; the prior
   image is reflashed if the run leaves the kit unbootable. Done 2026-11-17:
   CAPS passes; the PKA needed the HSI48 for INITOK (fixed); the hash and
   verify rows did not run, since no command of the unprovisioned image reaches
   them and `make hw-test` has no pin facts for the board. Next: a harness row
   (or a provisioned image) that drives SHA-256 and verify on the kit.
6. **Codex on PR #557**, one commit per finding. The include path: answered by
   a5a771f43. The soft fallback: the tier links `src/crypto/soft/verify_p256.c`
   renamed `tfw_crypto_soft_verify_p256` (micro-ecc with it), and the provider
   falls back to that, not to the soft provider's refusal. A timed-out PKA may
   still be running, so a timeout turns the PKA off for the rest of the boot.
   Tests in `test/unit/test_h5_pka.c`, which links the provider over the model:
   an INITOK that never rises and a timeout are answered by micro-ecc, and a
   timeout followed by a late completion never reaches the PKA again.
7. **Codex P1 on PR #557: consecutive HASH operations.** The model in
   `test/unit/test_h5_hash.c` stops being reset between operations: INIT
   restarts the core (drops the message and a digest in flight) but leaves
   DCIS and HR as they were, and DCIS rises some SR reads after DCAL, with HR
   holding the previous digest until then. Tests: distinct messages back to
   back on one model, and a timed-out operation followed by a good one. The
   driver (`src/crypto/stm32h5/h5_hash.c`) then clears DCIS after INIT
   (HAL `__HAL_HASH_CLEAR_FLAG`), so a stale DCIS never passes a later poll.
8. **Codex P1 on PR #557: a timed-out PKA is stopped before its RAM is
   written.** The model in `test/unit/test_h5_pka.c` raises BUSY at START and
   keeps it while an operation hangs; clearing EN aborts (HAL `HAL_PKA_Abort`)
   and drops BUSY and INITOK, unless the model's BUSY is stuck. Tests: a hung
   sign is aborted and its d and k are zero after, with no RAM write while
   BUSY; a BUSY that never clears gets no RAM write at all. The driver
   (`h5_pka_run`) on a timeout clears EN, waits for BUSY to fall, and re-runs
   `tfw_h5_pka_init` (EN, INITOK) before the sign's wipe; if either never
   comes, the wipe is skipped and the PKA left off (the provider already stops
   using it).
9. **Merge main (a2d59afa, the bench run and feature matrix).** One merge
   commit, no rebase; `docs/boards/stm32h573i-dk.md` keeps main's dated bench
   rows and adds this row's beside them, the newer dated evidence winning
   where both record the same row. No code change; the touched packages'
   unit tests re-run on the merged tip.
10. **Codex P1 on PR #557: register facts independent of the drivers.**
   `test/unit/h5_vendor_facts.h` restates every HASH and PKA fact the drivers
   use as a literal copied from the pinned ST sources above (file and line
   cited); the HASH and PKA models decode with those, not with
   `h5_crypto_regs.h`, and each suite adds a test asserting every driver
   constant equals its vendor literal. A wrong driver constant (say, no byte
   swap) then fails the host suites. No driver change.
11. **Codex P1 on PR #557: the HASH fallback through the provider.**
   `test/unit/test_h5_crypto_provider.c` links `provider.c`, the real
   `h5_hash.c` and the real `sha256.c`: a hung HASH still gives TFW_OK and
   the FIPS 180-4 "abc" digest from `tfw_crypto_sha256`, and a working one
   gives the same digest from HR. No driver change.

## Out of scope

Option bytes, TZEN, RDP, OTP, key storage in the SAES or the PKA, the Secure
Manager, the factory certificate, the AES peripheral, and the RNG as the
tier's entropy source.
