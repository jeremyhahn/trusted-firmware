# #548: a tone row measured on the board's own tone pin

## Objective

No hw-test row drives tone, and the CLI tone checks hard-code the AVR's pin
11, so tone on the ESP32-P4 (TFW_TONE_PIN 4, GPIO6) has never been measured.
Add the tone pin to the board pin facts, a hw-test row that starts a tone,
measures it back on the same pin and stops it, run it on the P4 with
`make hw-test`, and record the result in the board's feature matrix.

## Slices, in order

1. Pin facts: `tonePin` in `peerBoard` (sdk/go/cmd/tfwctl/e2e_pins_test.go):
   atmega328p 11 and atmega2560 10 (OC2A, the boards' board_profile.h), the
   P4 4 (GPIO6). Test: a host check that every board running the tone row
   has a tone pin that is not its PWM, ADC or no-PWM pin, and matches the
   board profile's TFW_TONE_PIN.
2. The row: `TestFirmwareTone` (e2e_firmware_test.go, listed in
   firmwareRowNeeds under FeatureTone). It sets the tone pin to output (so
   the pad's input stays enabled for the read-back), starts 1 kHz, runs
   `pulse-capture` on the same pin for a fixed count of edges, takes the
   frequency from the summed half periods and requires it within 5%, then
   `notone` and a capture that times out (the line is quiet). The CLI caps
   checks in e2e_caps_test.go run against tfwsim, a 328P, and keep its
   pin 11 through a named constant from the 328P's pin facts.
3. Hardware: `make hw-test` on the P4 (PORT=tcp:), the row's result with
   the date in docs/boards/esp32p4-poe.md; changelog.d/548-p4-tone-row.md.
   Departed 2026-11-17: the lane had the board's USB console only, which
   answers no wire, and not its address, so the row ran over the console,
   stopped at CAPS, and the matrix records that. The `tcp:` run is left.

4. Codex on PR #561, one commit per P1:
   - The Mega's ETH=1 image holds pin 10 (the shield's chip select), the
     tone pin: `partTonePinHeld` in its image; TestFirmwareTone needs the
     pin free, and TestFirmwareToneRefusesTheShieldsPin asserts
     RESERVED_PIN there. Test: the row selector on both images.
   - A TCP wire through meddler: cherry-pick 28be8666 (Target.Resets, no
     BOOT wait, meddler forwards SetReadDeadline) and eb76b3ed (meddler
     keeps a partial frame across a timeout). Test: Resets per wire.
   - The P4 list: `partTier` (CRYPTO is not none) gates Caps, EEPROM,
     I2CConfig and AttestRefusedUnprovisioned; the boot-event row skips a
     wire that does not reset; Sys takes the framing counters as a baseline
     when the board was not reset; Pin takes the LED pin's flags from the
     pin facts (cherry-pick bd0876fe). Test: the selector on the P4 image.

5. Codex request-changes at 1fb7761e, one commit per P1:
   - TestFirmwareToneRefusesTheShieldsPin runs only on hardware whose board
     image has partTonePinHeld (the simulator and the P4 leave the pin
     free); the P4 matrix line names `^TestFirmwareTone$`. Test: a host
     check that only the Mega's image holds the tone pin.
   - TestFirmwarePWM registers a cleanup that writes duty 0 to its PWM pin,
     so a TCP run that does not reset the board leaves the pin quiet.

6. Codex request-changes at 16930c64, one commit per P1:
   - TestFirmwareTone skips up front only where `tonePinHeld` (hardware and
     an image with partTonePinHeld); anywhere else RESERVED_PIN on the tone
     pin fails the row. Test: a host check of `tonePinHeld` per board.
   - TestFirmwareToneRefusesTheShieldsPin also sends TONE on the held pin
     and asserts RESERVED_PIN, so the check in src/caps/tone.c is covered.

7. Codex request-changes at b311e90d, one commit per P1:
   - The AVR's pulse capture (src/hal/avr/hal_pulse.c) counts polling
     loops, not calibrated microseconds, so TestFirmwareTone checks the
     frequency within 5% only on boards whose capture timestamps edges
     (`captureTimestamped`: the ESP32-P4's esp_timer). Everywhere else on
     hardware it keeps the start (30 edges) and stop (a timeout) checks and
     logs the uncalibrated figure. Test: a host check of
     `captureTimestamped` per board. Calibrating the AVR capture is a
     firmware change and stays out of scope.

8. Codex request-changes at 5a0f0ad5, one commit per P1:
   - The P4 image builds ESP_PULSE=rmt: hal_pulse_rmt.c opens its RX
     channel without io_loop_back and claims the GPIO as an input, which
     drops the LEDC output on the same pin. TestFirmwareTone captures on
     the tone pin only where the capture keeps an active output
     (`captureKeepsOutput`: the AVRs' polling capture); on the P4 it checks
     TONE and NOTONE answer OK and logs that the read-back needs the RMT
     channel's io_loop_back or a wired input, a firmware or bench change
     out of this lane (no hardware here). Test: a host check of
     `captureKeepsOutput` per board.

9. Codex request-changes at 5a3ed41e, one commit per P1:
   - On the P4 the row ran no read-back yet passed, and the matrix claimed
     a measured 1000 Hz. The brief's failure outcome instead: on hardware
     where the capture cannot read the tone back (`toneReadBackGap`: the
     P4's RMT capture drops the output), the row still checks TONE and
     NOTONE answer OK and then fails, naming the gap, so a P4 run can no
     longer record verification. The P4 matrix line becomes "fails: no
     read-back" with the issue to file (a lane files none). Test: a host
     check that `toneReadBackGap` names the P4 and is empty on the AVRs.

10. Codex request-changes at 8a576771 (docs only, no test):
   - The P4 tone line names its filed follow-up, #573 (RMT capture drops
     the LEDC output), and says plainly the row has not yet run over
     `tcp:` (this lane has no hardware), so it is a tracked failure, not a
     verification. The other matrix lines name their filed issues: #574
     Pin, #575 EEPROM, #576 Caps and I2CConfig.
11. Codex request-changes at cfd767fc (hardware, no code):
   - The tone row runs once over the P4's TCP wire: CAPS first over
     `tcp:<board>:21574` to check the running image reports TONE (if not,
     the dated result goes in the matrix and the lane stops), then
     `make hw-test ... HW_TEST_RUN='^TestFirmwareTone$'`. The tone line
     records the dated output and the actual result, #573 kept if the
     read-back fails. A connection dropped between tests is the TCP accept
     race on PR #568, named, not fixed here. No flashing in this lane.
     Departed 2026-11-17: the lane was handed no board address (the
     static address lives in an untracked overlay the lane does not have),
     so no CAPS and no row ran; the matrix records that, and the run waits
     for a lane given `<board>`.
12. #573, the read-back (firmware, host only, Refs #573):
   - hal_pulse_rmt.c opens the RX channel with `flags.io_loop_back`, so
     the IDF connects the RMT input through the GPIO matrix without
     detaching the LEDC output on the pin, and a capture on the tone pin
     reads the LEDC waveform. Test: the esp32p4 build with ESP_PULSE=rmt
     compiles. `toneReadBackGap` and the matrix row stay until a hardware
     run verifies it; #573 closes after that run.
13. The Codex P1s at d77a40e: io_loop_back only on the pin the LEDC tone
    drives (`tfw_esp_tone_gpio`), never on a plain input (host tests: tone
    pin, other pin, PULSE_IN); `captureKeepsOutput` is true on the P4, so
    TestFirmwareTone runs the frequency and silence checks there. The matrix
    keeps "no TCP tone run" until the hardware run.
14. Merge of main (#567, the P4 and STM32 rows): main's helpers replace
    this branch's (`noLED`/`ledPinFlags` for `ledFlags`, `tier: cryptoTier`
    for `partTier`, `partTCP` for the Sys row, `toneFrequencyFits` for
    `captureTimestamped`/`toneReadBackGap`, `openTCP` in peer), and main's
    dated P4 tone run replaces the "no TCP tone run" matrix line. Test: the
    P4 row selector follows main's list.

## Out of scope

Tone on boards other than the P4 on hardware; a firmware change if the
read-back fails (it goes in the report and the matrix); fuses, eFuse writes,
serial break.
