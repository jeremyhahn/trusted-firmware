# 549: hw-test rows know what a CRYPTO=none board answers

## Objective

On the ESP32-P4 bench image (`CRYPTO=none`) the rows `Caps`, `EEPROM`,
`I2CConfig` and `AttestRefusedUnprovisioned` fail only because they carry no
facts for the none tier (`docs/boards/esp32p4-poe.md:121`–`123`). Each row
branches on the tier CAPS reports and expects what the firmware answers.

## None-tier expectations

| Row | None tier expects | Source |
|---|---|---|
| `AttestRefusedUnprovisioned` | UNSUPPORTED (`0x7`), not NOT_PROVISIONED | `docs/boards/esp32p4-poe.md:84`–`86`, `:123`; `src/crypto/none/provider.c` `tfw_crypto_sign` |
| `Caps` | tier `none`, algorithms empty; ATTEST still reported | `docs/boards/esp32p4-poe.md:122`; `src/crypto/none/provider.c` `tfw_crypto_algorithms` returns 0 |
| `EEPROM` (reserved read) | the reserved read is answered, as on the soft tier: no auth gate | `docs/boards/esp32p4-poe.md:121`; `src/core/auth_session_none.c` `tfw_auth_gate` returns OK (`mk/firmware.mk:281`–`290`) |
| `I2CConfig` | the clock is applied, as on the soft tier; only the element refuses | `docs/boards/esp32p4-poe.md:122`; `src/caps/bus.c:121` |

The brief named a "protected-read refusal" for EEPROM; the firmware does not
refuse it on the none tier (the gate is the element's alone), so the row
expects the answer the source gives. Hardware confirmation is the next P4
hardware lane's.

## Slices

1. `AttestRefusedUnprovisioned`: body moved to a row function taking the
   device; none tier expects UNSUPPORTED.
2. `Caps`: none tier expects empty algorithms.
3. `EEPROM`: none tier expects the reserved read answered.
4. `I2CConfig`: none tier expects the clock applied.
5. Host tests: each row function run against a fake none-tier peer and a
   fake soft-tier peer (`fakedev_test.go`'s frame server); changelog.

## Codex P1s on PR #559 (one commit each)

6. TCP reply wrapper: `meddler` forwards `SetReadDeadline` and keeps a
   partial frame across a timeout; a TCP target (`peer.Target.Resets`
   false) waits for no BOOT. Cherry-picked from the #547 lane; host test: a
   silent TCP peer under the wrapper returns within the bound.
7. Persistent board state: on a target that does not reset, the boot-event
   row and the framing-counter row assert what a running board answers
   (BOOT not expected on connect; counters checked as deltas, not zero).
   Host test: the rows run in sequence against a fake peer that keeps state.
8. Pin row: the LED flag comes from the board's pin facts (false for the
   P4's plain GPIO stand-in); the digital flag is asserted on its own.
9. State-row tests build with `tfwsim`: `e2e_state_rows_test.go` calls
   `bootEventRow` and `sysRow`, defined in the `tfwsim`-tagged
   `e2e_firmware_test.go`, so it carries the same tag (untagged
   `sdk-coverage` and `sdk-lint` compile again).

## Out of scope

Running the rows on the board; the other failing P4 rows (boot event, CLI
CAPS hang, Ethernet dial, OTA); a `tfwsim` built `CRYPTO=none`.
