# 550: boot-event and Sys rows over a tcp: link

## Objective

Over `PORT=tcp:<ip:port>` (ruling 768) hw-test has no DTR, so it cannot reset
the board between rows. Two rows then fail for a reason that is not the
firmware's:

- `TestFirmwarePingDeliversTheBootEventWithNoBootWait` needs a fresh boot, and
  the board is found running;
- `TestFirmwareSys` asserts zero framer CRC/format errors, but
  `TestFirmwarePingAfterAMalformedBurst` leaves those counters raised on the
  same, never-reset board.

## The reset rule

- A tcp: link resets the board only through `RESET_PORT` (make variable,
  `TFW_HW_RESET_PORT` in the suite): a serial port used for nothing but the
  DTR pulse (`peer.ResetPulse`). The row pulses it, then dials the tcp:
  endpoint again until the rebooted board accepts (`peer.StartBound`), and
  checks the boot event as before.
- Without `RESET_PORT` the boot-event row skips with a reason that names the
  link and the variable. It never passes without a boot it observed.
- A serial or QMP link is unchanged: it resets as it always did.

## The order rule

Row order does not matter: `TestFirmwareSys` reads `sys` before and after its
own commands and asserts the framer counters did not move (a delta), so the
counters a malformed burst leaves on a board nobody reset do not fail it.

## Slices

1. Sys delta (`e2e_firmware_test.go`): `sysCountersHold` reads `sys`, runs a
   ping, reads `sys` again, asserts the CRC and format counters equal.
   Host test: a malformed burst on a simulated peer, then the Sys check on
   the same peer passes, and the counters are non-zero (the burst counted).
2. Boot-event reset (`e2e_firmware_test.go`, `mk/go.mk`): `bootEventLink`
   returns the link to the board after a reset, or a skip reason.
   Host tests on a simulated tcp peer (a TCP listener bridged to the
   software simulator): with a reset port the fake pulse runs before the dial
   and the boot event arrives; without one the reason names
   `TFW_HW_RESET_PORT`.
3. Changelog fragment.
4. Boot event before the first accept (Codex P1 on #558). The ESP32 sends
   BOOT before its loop accepts a client, and `hal_uart.c` dropped every byte
   sent while no client was connected, so no post-reset connection could see
   BOOT. Fix in the firmware (smaller than skipping the row): until the first
   client is accepted after boot, `tfw_hal_uart_tx_try` keeps the bytes in
   `tx_buf` (bounded by `TX_BUF`; on overflow the held bytes are discarded
   whole, never sent cut) and the first accept sends them. After a client has
   been accepted, bytes sent with no client are dropped as before.
   Host test: the simulated tcp peer models that ordering (it reads the
   simulator from start, holds pre-accept output under the same rule, drops
   output with no client after the first one); without the hold it fails.
5. Codex P1 on #558: test the hold in `hal_uart.c` itself, not only in its Go
   model. `test/unit/test_esp_wire.c` (the mock-lwIP harness) gains: BOOT
   sent before any host is accepted arrives whole at the first host; held
   output past `TX_BUF` is discarded whole; after the first host goes, output
   with no host is dropped. `tfw_hal_uart_init` re-arms the hold (init is
   boot), so each test starts as a booted device. Then `serveESPWire` accepts
   only after its reader has taken the first simulator output, so the Go row
   always exercises the held path rather than racing it.

## Out of scope

- Hardware confirmation of the boot event over tcp: the next P4 hardware
  lane.
- Whether a DTR pulse alone resets the ESP32 (its auto-reset circuit drives
  EN from RTS, GPIO0 from DTR): the hardware lane checks it, and the pulse
  moves to RTS in `pulseReset` if it does not.
- Any change to `internal/peer`.
