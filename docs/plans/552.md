# #552: the OTA rows on the ESP32-P4, on a soft-tier image

Objective: the ESP32-P4's OTA SPEC rows (write, trial, confirm, roll back)
run on the board, each with a dated result and its evidence in
`docs/boards/esp32p4-poe.md`'s feature matrix (ruling 768). The bench HIL-0
image is `CRYPTO=none`, which has no operator session, so no OTA row has run.

## Slices, in order

1. Toolchain: ESP-IDF v5.5.5, esptool / espefuse v5.6.0 outside the clone
   (docs/multi-arch/adr-esp-idf-integration.md); not in the lane image.
2. Build: `make esp32-build BOARD=esp32p4-poe CRYPTO=soft
   ESP_SDKCONFIG_EXTRA="boards/esp32p4-poe/sdkconfig.hil0 <overlay>"`; secure
   boot and flash encryption off, so first boot burns no eFuse.
3. Before any write: `espefuse summary` (read only) and a read-back of the
   part, kept outside the tree: the restore image.
4. Flash the data partitions, app, `tfw_plat.bin`, bootloader and table as in
   docs/development/bench/esp32-p4.md; never `erase-flash`, never an eFuse.
5. Operator session: `OPERATOR_KEY` provisioned the way the auth rows expect.
6. Run `make hw-test BOARD=esp32p4-poe PORT=tcp:<board>:21574 HW_TEST_RUN='OTA'`;
   a row-side defect in `sdk/go/cmd/tfwctl` is fixed with its test.
7. Record each OTA row's result, date and evidence in the matrix; no address,
   MAC or device path in added lines.

## As run, 2026-11-17

The soft tier links no operator session (`mk/firmware.mk`, issue #4):
`OTAActivate`, `OTAConfirm` and `OTAInfo` are out of a soft image's row list.
The read-back covered the region the flash writes (first 0xA2000 bytes).

## Codex review of PR #564

1. The OTA write refusal was the row's image (no ESP app-image magic): the
   matrix cites #562 (PR #567), which stages an ESP-IDF app image.
2. The soft tier needs no operator session (`tfw_auth_gate()` is TFW_OK):
   trial/confirm/roll back are `not run`, waiting for a signed image (#562).
3. Wrapped TCP wire hung on the boot wait: cherry-picks of 28be8666 and
   eb76b3ed (read deadline kept, partial frame kept across a timeout).
4. Mega ETH=1 tone pin D10 is TFW_PIN_ETH: TestFirmwareTone skips partToneEth
   images; a refusal row checks RESERVED_PIN there.
5. `HW_TEST_RUN='Tone'` matched the refusal row: both rows read partToneEth
   (unit test); the board page's command is anchored `^TestFirmwareTone$`.
6. The meddler's partial-frame buffer: a TCP test cuts a frame in its header
   and body across a read timeout; one response decoded and rewritten.
7. P1 (P4 row list, e2e_rows_test.go): cherry-pick of 009425178 from #558:
   the CRYPTO=none P4 run leaves out Caps, EEPROM and I2CConfig (cryptoTier).
8. P1 (connections that do not reset, e2e_rows_test.go): the P4 is reached
   over TCP, which keeps the running board. The BOOT-event row and the Sys
   row (zero framing counters, broken by the malformed-burst row before it)
   need a fresh boot; they need a resetting connection and leave the P4 run.
   Unit test: the P4 run leaves both out, the AVR boards keep them.
9. P1 (hardware trial/confirm/roll back, docs/boards/esp32p4-poe.md:130): not
   a host change. It needs the P4, a stageable signed image (#562) and its
   signing key; the rows run in the hardware lane after #562 lands.
10. P1 again (same line, second review): the matrix line names the soft-tier
   hardware rows still to add (OTA_AUTH, then stage, activate into the trial,
   confirm; and a trial left unconfirmed that rolls back on reset) and says
   #552 is not complete until they pass on the P4 with dates. No host rows in
   this lane: without a stageable signed image (#562) a soft-tier trial row
   can only fail at OTA_STAGE, and this lane runs no hardware.
11. P1 (P4 row list, e2e_rows_test.go:125): `Pin` wants an LED pin; the P4's
   board.c marks GPIO32 digital only (`partNoLED`). `AttestRefusedUnprovisioned`
   wants NOT_PROVISIONED, a tier's answer; the none tier answers UNSUPPORTED
   (`cryptoTier`). Unit test: the P4 run leaves both out, the AVR rows keep
   theirs (328p/2560 are provisioned, so that row stays out there as before).
12. Merge of main after #567: main's OTA write line (the ESP-IDF app image,
   refused at the app signature check) replaces this PR's; main's `openTCP`
   redial is kept and `Open` dials through it; main's `noLED` keeps the P4's
   `Pin` row, asserting pin 11 digital without LED, in place of `partNoLED`;
   main's `partTCP`, `partTonePinHeld` and `attestRefusal` replace this PR's
   `partNoReset`, `partToneEth` and the attest row's exclusion (items 4, 8, 11).

13. P1 (round 5, docs/boards/esp32p4-poe.md:137): the hardware run, lane
   hw-564a, after the merge of main 7553dea36. Soft-tier image without the
   static-address overlay, sealed with the image key of the board's layer-0
   build, flashed app-only at 0x20000 (ruling 945 (3): a full-image flash is
   provisioning, never PR evidence; the 2026-11-17 full flash is no longer
   this PR's evidence). `HW_TEST_RUN='OTA'`, then the full `make hw-test`;
   trial, confirm and roll back driven through `tfwctl` with that sealed
   image and its activate/confirm authorization (the image key's ES256 over
   the Sig_structure), since no host row does it yet. Each row gets a dated
   verified or failed line; no firmware change.

## Out of scope

eFuse writes of any kind, secure boot, flash encryption, the UDS identity;
the board-dials Ethernet rows (`HW_ETH`); the other failing matrix rows;
any flash outside the app partition; new host rows.

## Owner ruling 1243 (2026-11-24)

#563, option (c): "Record the OTA trial, confirm and roll back rows as not
applicable on the ESP32-P4 soft tier in SPEC ota." The P4 has no secure
element and the operator session links only on element tiers, so the hw-test
rows `TestFirmwareOTAActivate` and `TestFirmwareOTAConfirm` are not applicable
on the P4 soft tier, not owed. Items 9, 10 and 13 are settled by it: no
soft-tier hardware rows are added, and the by-hand run of lane hw-564a
(2026-11-19) stays the record in `docs/boards/esp32p4-poe.md`.
