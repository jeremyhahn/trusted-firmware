# #562: ota-stage on a soft-tier ESP32-P4 stages the image

Objective: the OTA write row (`OTAAuthLetsTheCommandPastTheGate`) passes on
the ESP32-P4's soft-tier image, with a dated result in
`docs/boards/esp32p4-poe.md` (ruling 768).

## Reproduction (host, before any edit)

The status the board answers, `crypto provider failed`, is TFW_ERR_CRYPTO.
On the ESP32 port it does not come from `src/crypto/soft`: the stager is
`src/hal/esp32/hal_ota.c`, whose `from_esp` maps ESP-IDF's
`ESP_ERR_OTA_VALIDATE_FAILED` to TFW_ERR_CRYPTO. ESP-IDF's `esp_ota_write`
answers that on the first chunk whose first byte is not the app-image magic
0xE9, and `esp_ota_end` answers it for an image `esp_image_verify` refuses
(header, chip id, segment checksum, appended SHA-256). The host mock models
the same rules (`test/mock/esp_ota_mock.c`). The row stages
`stageImageFor(512, 200, board)` (`sdk/go/cmd/tfwctl/e2e_ethernet_test.go`),
whose first byte is 0x03: no ESP32 stager can take it, on any crypto tier.
The defect is the row's image, not the firmware.

## Slices, in order

1. Row: `stageImageFor` builds, for an ESP32 board id (`BoardESP32P4PoE`,
   `BoardESP32QEMU`), an image ESP-IDF's verifier takes: a 24-byte app
   header (magic 0xE9, the board's chip id, `hash_appended`), one segment
   at a load address neither mapped nor loaded, the XOR checksum padded to
   16, the SHA-256 of all of it, then the TFIM trailer as before. Other
   boards keep today's image. Test: `TestStageImageForESP32IsAnAppImage`
   checks the magic, chip id, checksum and appended hash; it fails on
   today's image and passes after (`make sdk-test`).
2. Hardware: the board runs the #552 soft-tier image (no rebuild, no flash
   needed for a row-side fix): `espefuse summary` (read only),
   `make hw-test BOARD=esp32p4-poe PORT=tcp:<board>:21574
   HW_TEST_RUN='OTAAuth'`, `espefuse summary` again, identical.
3. Record: the OTA write row's matrix line gets the dated result; changelog.

## As run, 2026-11-17

Slice 1 landed; ESP-IDF 5.5 also reads `esp_app_desc_t` at the segment's
start (its eFuse block revision range), so the image carries one. On the
board the image now writes and verifies to the signature: the soft-tier
build verifies app signatures on update, and `esp_ota_end` refuses an
unsigned image (`image valid, signature bad`), still answered as
TFW_ERR_CRYPTO. No ESP-IDF in the lane image, so no rebuild or flash: the
board ran the #552 image. Next slice: the row stages an image signed with
the build's image key (the build's own app image, or one signed with
espsecure), named to the row by a hw-test variable.

## Codex request-changes on #567 (lane cdx-567b)

4. Rows: the caps-bit refusal row (`meddler` hides `SetReadDeadline` and
   waits for a BOOT a TCP connect never sends) leaves the P4 list: a new
   `partTCP` image part, the row needs `not: partTCP`. Test:
   `TestBoardRunLeavesTheMeddlerRowOffATCPBoard`. The wrapper fix (no BOOT
   wait without a reset, deadlines through meddler) landed on main, so the
   next slice (#48, branch `row/48-p4-meddler-tcp`) puts the row back on TCP
   boards: the row needs nothing, the P4 list runs it. Tests:
   `TestBoardRunRunsTheMeddlerRowOnATCPBoard`, and
   `TestMeddlerRefusesAttestCSRWithoutABoot` (a net.Pipe board that sends no
   BOOT, boot wait off and on, a 2 s watchdog; it fails through the
   watchdog without the meddler's `SetReadDeadline` pass-through). Out of
   scope: the bench run of the row on a P4; no board was flashed.
5. Tone: AVR `pulse-capture` reports polling-loop counts, each at least
   1 us, so counts understate time and the frequency only reads high. On
   the AVR boards the row bounds it from below (no lower than 5% under the
   tone); elsewhere the 5% band stays. Test: `TestToneFrequencyFits`.
6. QEMU chip id (Codex P1, `esp_image_test.go:44`): esp32-qemu runs two
   machines, esp32c3 by default, and the stage image carried the ESP32's
   chip id for both. `hw-test` passes `ESP_TARGET` as `TFW_HW_ESP_TARGET`;
   the image takes the chip id of that machine (esp32c3 when unset). Test:
   `TestStageImageForESP32IsAnAppImage` on both machines, ids written out.

## Codex request-changes on #567 at ee76c5eb (lane cdx-567d)

7. Tone pin (Codex P1, `e2e_firmware_test.go:382`): the Mega's ETH=1 image
   marks the tone pin, D10, TFW_PIN_ETH, so MODE answers RESERVED_PIN. The
   same fix as #561 (row/548-p4-tone-row) carries: `partTonePinHeld` on the
   Mega image, `TestFirmwareTone` needs it absent (and skips only on
   hardware whose image holds it), and `TestFirmwareToneRefusesTheShieldsPin`
   asserts RESERVED_PIN for MODE and TONE there. Tests:
   `TestOnlyTheMegaImageHoldsTheTonePin`, `TestTonePinHeldOnlyOnTheMegaHardware`,
   the Mega's run lists in `TestEachAVRBoardRunsTheRowsItsImageServes`.
8. Reset rows (Codex P1, `e2e_rows_test.go:111`): a TCP connect resets
   nothing, so no BOOT event arrives, and the framer counters keep the
   malformed burst's errors across reconnects. The BOOT-event row and
   `TestFirmwareSys` need `not: partTCP`. Test:
   `TestBoardRunLeavesTheResetRowsOffATCPBoard`. A TCP form of the sys row
   (counter deltas) is a later slice.

## Codex request-changes on #567 at 4c8e2cf5 (lane cdx-567e)

9. None tier (Codex P1, `e2e_rows_test.go:126`): the P4 image is
   CRYPTO=none. #558's canonical answer (0094251788, cherry-picked):
   `noneTier` for the image, `cryptoTier` on Caps, EEPROM and I2CConfig,
   whose facts are software and element only. The unprovisioned attest
   row answers UNSUPPORTED on a device whose CAPS reports no tier, and
   NOT_PROVISIONED on a tier. Test:
   `TestTheESP32P4RunLeavesOutTheRowsWithNoNoneTierFacts`.
10. LED pin (Codex P1, `e2e_pins_test.go:96`): the P4's pin 11 is plain
    digital. Board pin facts say whether the board has an LED; on a board
    without one `TestFirmwarePin` asserts the GPIO's own flags (digital,
    no LED). Test: the P4's facts carry no LED and expect PinDigital alone.
11. Untagged build (Codex P1, `e2e_rows_test.go:381`): `attestRefusal` moves
    from the tfwsim-tagged `e2e_firmware_test.go` to the untagged
    `e2e_rows_test.go`, so the plain unit build, coverage and vet compile.
12. Reconnect race (Codex P1, `peer.go:220`): the fix PR #568 carries is
    cherry-picked, not rewritten: the ESP32 HAL reads the old host's
    hangup before it weighs a pending connection (`hal_uart.c`), and the
    peer dials again when the board closes a fresh TCP connection at once.
    Tests: those the two commits bring (old socket EOF with a replacement
    pending; a board that closes the first dial, and every dial).
