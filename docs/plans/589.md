# Plan 589: the ESP32-P4 provisioning procedure as its own document

## Objective

Ruling 945 (3): a full-image or bootloader/partition-table flash is a
provisioning procedure, documented separately and never part of an Ethernet
PR's hardware evidence. This row writes that procedure for the ESP32-P4 PoE
board from the hw-568f record (the full-image run #568 dropped from its
evidence) and the build (`mk/arch/esp32-targets.mk`).

## Slices

1. `docs/boards/esp32p4-provisioning.md`: when provisioning is needed (a new
   board, a new image key); the files a build produces (bootloader,
   partition table, `tfw_plat.bin`, the sealed app); the write order and
   offsets as hw-568f did them; how the image key is created and kept, and
   why every later app-only flash must be sealed with the same key; the
   `espefuse summary` before and after; what is out of scope.
   A "Provisioning" pointer in `docs/boards/esp32p4-poe.md`, and the page
   in the `boards/` row of `docs/README.md`.
   Test: markdown only; every relative link in the touched files resolves.

## Out of scope

- eFuse burns, secure boot or flash encryption enablement, `erase-flash`
  (CA 583), and owner-only steps.
- Any change to `docs/SPEC.md`, `ROADMAP.md`, `.github` or `build/`.
- The bench record itself (`docs/development/bench/esp32-p4.md`), which keeps
  the dated runs.
