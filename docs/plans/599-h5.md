# #599 stm32h5: a HASH timeout switches SHA-256 to software for the boot

Objective: the Codex P2 on #557. `tfw_crypto_sha256` in
`src/crypto/stm32h5/provider.c` tried the HASH peripheral on every call and
fell back to `tfw_sha256` only after the status-poll timeout, so a hung HASH
cost the full timeout on every digest of the boot. docs/plans/544.md promises
the switch, and the PKA path already makes it with `pka_up`.

## Slices

1. Test first (`test/unit/test_h5_crypto_provider.c`): `setUp` runs
   `tfw_crypto_init` (a fresh boot per case) and the HASH model counts SR
   reads. With the HASH hung, the first call returns the right digest; a
   second call adds no SR reads and still returns the right digest; after
   `tfw_crypto_init` the peripheral answers again (8 HR reads). The
   unconditional `tfw_h5_hash_sha256` call fails the second case.
2. Fix: `static uint8_t hash_up`, set in `tfw_crypto_init`, cleared on the
   first HASH failure; while it is clear `tfw_crypto_sha256` runs
   `tfw_sha256` alone. Changelog fragment `changelog.d/599-h5-hash-fallback.md`.

## Out of scope

- Re-probing the HASH within a boot (only `tfw_crypto_init` brings it back).
- The tier guard of PR #619 (row/599-crypto-tier-guard) and its files.
- Bench timing of the poll timeout on the DK.
