# 608: the TrustZone-M secure world on TF-M (ruling 1024 (a))

Objective: build the STM32H5 and nRF54L15 secure world on upstream TF-M
Profile Medium, with our DICE layer as an Application RoT partition, in place
of a secure monitor of our own (ruling 935's option (a)). Owner, verbatim:
"the TrustZone-M secure world is built on Trusted Firmware-M with our DICE
layer on top, not a secure monitor written from scratch." Ruling 935's other
points stand: no vendor secure world, no PSA token (TF-M without its Initial
Attestation partition, or with it not exposed). Refs #590.

## TF-M v2.3.1 platform ports

The pin is `scripts/tfm-measure.sh`'s: tag TF-Mv2.3.1, commit 0b40d780.
Found from that commit's `platform/ext/target` tree (shallow fetch, out of
tree) on 2026-11-20.

| board          | TF-M v2.3.1 port                                         |
|----------------|----------------------------------------------------------|
| STM32H573I-DK  | yes: `stm/stm32h573i_dk` (on `stm/common/stm32h5xx`)     |
| NUCLEO-H563ZI  | no board port; `stm/common/stm32h5xx` is the family base  |
| nRF54L15       | yes: `nordic_nrf/nrf54l15dk_nrf54l15_cpuapp`              |
| mps2-an505     | no: `arm/mps2` has `an519` and `an521` only               |

Settled for slice 2 (coordinator):

1. The QEMU target is TF-M's upstream `arm/mps2/an521`, run as
   `qemu-system-arm -M mps2-an521`; no AN505 port of our own. The mps2-an505
   targets and `src/hal/cortex-m/tz/` stay as they are; slice 3 replaces the
   monitor.
2. The NUCLEO-H563ZI gets a board port derived from `stm/stm32h573i_dk` in
   slice 4 (the H563 has no SAES or PKA, so its crypto config differs).

## Slices, with their tests

1. This plan; ADR #15 and the MCU DICE ADR amended to (b1). Docs only.
2. TF-M built out of tree (`scripts/tfm-build.sh`, the pins shared with
   `scripts/tfm-measure.sh`) for an521 and the STM32H573I-DK: Profile Medium,
   BL2 on, Initial Attestation off, tf-m-extras' example non-secure app.
   Tests: `make tfm-qemu-test` (test/integration/cortex-m/qemu_tfm_test.sh)
   boots bl2, tfm_s and ns on mps2-an521 to "Booting TF-M" and the NS app's
   first line; `make tfm-image TFM_BOARD=stm32h573i-dk` builds the signed
   images. Status: code done, gates run in coordinator verify (the lane
   image has no Arm toolchain or QEMU). The verify records the image sizes
   (`$TFM_WORK/out/<board>/sizes.txt`) for both boards here.
3. The DICE layer as an Application RoT partition (CDI, DeviceID key, alias
   key) with a PSA client API for the non-secure side. Tests: host unit tests
   of the partition logic; the QEMU integration target calls it and checks
   the alias certificate against go-xkms device-attest-01's dice format.
   Status: partition core done and host-tested (`src/tz/dice_partition.c`
   dispatch and start, `src/tz/tz_s_client.c` NS client over `psa_call`,
   `test_dice_partition`); manifests in `src/tz/tfm/`. The TF-M glue is
   done and host-tested (`src/tz/tfm/tfw_dice_partition.c`: UDS by
   HKDF-SHA256 from `TFM_BUILTIN_KEY_ID_HUK`, info "tfw-dice-uds-v1";
   measurement = Measured Boot slot 3 (RT_1, the NS image), refused unless
   locked and a 32-byte SHA-256; `src/tz/tfm/CMakeLists.txt`;
   `test_tfw_dice_glue`). The build half is in code: `scripts/tfm-build.sh`
   turns on TFM_PARTITION_TFW_DICE and tf-m-extras' Measured Boot
   (TFM_EXTRA_MANIFEST_LIST_FILES, TFM_EXTRA_PARTITION_PATHS,
   TFM_PARTITION_MEASURED_BOOT, CONFIG_TFM_BOOT_STORE_MEASUREMENTS,
   MCUBOOT_DATA_SHARING); the NS app's check
   (`src/tz/tfm/ns/tfw_dice_ns_check.c`, joined by a CMAKE_PROJECT_INCLUDE
   hook in the work directory and `--wrap=psa_framework_version`) prints
   "tfw-dice: deviceid ok", which `qemu_tfm_test.sh` requires. Status:
   glue, flags, NS call and QEMU check in code; gates (`make tfm-qemu-test`,
   `make tfm-image TFM_BOARD=stm32h573i-dk`) in coordinator verify.
   Codex round 4 P1 #1 is fixed: `tfw_dice_partition_init()` installs a
   fail-closed PSA blinding RNG for micro-ecc
   (`uECC_set_rng(tfw_dice_blind_rng)`, which succeeds only when
   `psa_generate_random()` returns PSA_SUCCESS) before it starts the
   service; `test_init_installs_a_psa_blinding_rng` and
   `test_a_failing_psa_rng_refuses_alias_sign` in
   `test/unit/test_tfw_dice_glue.c` cover it.
   The QEMU alias check (Codex round 5): the NS check also fetches the alias
   key, the paged alias certificate over nonce 00..1f and an alias signature
   over digest 20..3f and prints them as hex; `qemu_tfm_test.sh` requires
   "tfw-dice: alias ok" and runs `xkms/cmd/tfm-dice-check` (`xkms/tfmdice`,
   unit-tested: DeviceID signature, alias-pub, eat_nonce read with go-xkms
   `dice.Challenge`, alias r||s). Status: code done; the gate `make
   tfm-qemu-test` runs in coordinator verify. `xkms/cmd/tfm-dice-check` has
   a testable `run()`, and `main_test.go` covers its argument, file and
   check refusals; `xkms/tfmdice/check_test.go` covers the alias-key,
   digest, signature-algorithm and missing-evidence refusals.

Decided in slice 3 (r109, for the coordinator to confirm): the UEID is
HMAC-SHA256(UDS, "tfw-dice-ueid-v1") cut to 16 bytes; the service SID is
0xD1CE0000, stateless; the partition answers a `tfw_status_t` as the
`psa_call` status; enabling tf-m-extras' Measured Boot partition goes beyond
slice 2's partition set.
4. The NUCLEO-H563ZI and nRF54L15 builds, and the hardware run on the
   STM32H573I-DK (probe-dependent), with the board pages updated.
   Tests: `scripts/test_tfm_build_boards.py` (tfm-build.sh takes
   nucleo-h563zi; an unknown board's usage names all three; the port's
   CRYPTO_HW_ACCELERATOR is OFF). Status: the NUCLEO-H563ZI build is in
   code: `src/tz/tfm/platform/nucleo_h563zi`, TF-M's stm32h573i_dk out of
   tree with software crypto (no SAES or PKA), the console on USART3 and the
   device define left at STM32H573xx (TF-M v2.3.1 ships only that CMSIS
   header). The gate `make tfm-image TFM_BOARD=nucleo-h563zi` runs in
   coordinator verify (the lane image has no Arm toolchain). The port leaves
   option bytes to the owner: TFM_ENABLE_SET_OB is off, so BL2 only checks
   them (`scripts/test_tfm_nucleo_option_bytes.py`). Status: slice 4's
   retirement of the own TrustZone-M split is done (commit 30a70dad):
   `src/hal/cortex-m/tz/` (the secure and non-secure mains, the regions,
   the veneer, the mps2-an505 and NUCLEO-H563ZI maps, the console and the
   MPS2 SoC glue), `mk/arch/cortex-m/tz_s.ld` and `tz_ns.ld` and the tz-*
   targets in `mk/arch/cortex-m-targets.mk` are deleted, the two boards'
   `TZ_MAP` lines give way to a pointer at the TF-M targets, and
   `make firmware TZ=1` now stops with "TZ=1 is retired (#608): use make
   tfm-image" (`mk/firmware.mk`). Remaining: the
   nRF54L15 build and the hardware run.
   Blocker, nRF54L15 (found 2026-11-24 from the pin, read only): TF-M
   v2.3.1's `nordic_nrf/nrf54l15dk_nrf54l15_cpuapp` takes
   `common/nrf54l15/config.cmake`, which includes `common/nrf54l/config.cmake`,
   and that sets `BL2 OFF CACHE BOOL ... FORCE` (and `NRF_NS_SECONDARY OFF`
   FORCE), overriding `-DBL2=ON`. The board's `if(BL2)` branch names a
   `partition` directory the port does not ship. With no BL2 there is no
   MCUboot boot record and no MCUBOOT_DATA_SHARING area, so Measured Boot
   has no slot 3 and the DICE partition would stay unprovisioned. Upstream
   expects MCUboot built outside TF-M (Zephyr/NCS), and the port fetches
   hal_nordic `nrfx-4.0.1` from GitHub. Per ruling 1024 no own boot or
   shared-data code is added; `scripts/tfm-build.sh` does not take
   nrf54l15-dk until the coordinator rules (options: an external MCUboot
   build that hands TF-M the shared data, a later TF-M with BL2 on nRF54L,
   or the board without the DICE measurement).

The slices follow issue #608's checklist, in this order: slice 1, the ADRs
and this plan (docs only); slice 2, the TF-M build integration for the
STM32H573I-DK; slice 3, `dice_service.c` as an Application RoT partition,
with `tz_s_api.h` as an NS client over TF-M; slice 4, the retirement of
`tz_s_main.c`, `tz_regions.c`, `tz_veneer.c`, the TZ maps and
`tz_s.ld`/`tz_ns.ld`, and the nRF54L15 port; and the #590 second slice
folded in here (#899).

PR #899 (row 590) is folded in: its Go SDK DICE evidence verifier and
service vectors are taken; its TFW_NSC DICE calls on the mps2-an505 monitor
are not (ruling 1024: TF-M is the secure world, slice 4 drops the monitor).

## Open

- Codex round 4 P1 #2 (`sdk/go/diceevidence.go:103`,
  `VerifyDICEAttestation`) conflicts with `docs/SPEC.md:23` and the
  dice-attestation row (`docs/SPEC.md:37`), which put evidence verification
  in go-xkms; it is an owner question and is not changed here.
- The gates `make tfm-qemu-test` (which runs the DICE and alias checks) and
  `make tfm-image TFM_BOARD=an521|stm32h573i-dk|nucleo-h563zi` need the TF-M
  toolchain image and run in coordinator verify.
- The nRF54L15 BL2 blocker (item 4) waits on a coordinator ruling; the
  STM32H573I-DK hardware run needs the probe.

## Out of scope

The ESP32-P4 (ruling 1024 (b), row #606), the AVR path, the `stm32h5` SPEC
row wording (its own SPEC change), CI workflow changes, option bytes, TZEN,
RDP and lock bits.
