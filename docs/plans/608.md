# 608: the TrustZone-M secure world on TF-M (ruling 1024 (a))

Objective: build the STM32H5 and nRF54L15 secure world on upstream TF-M
Profile Medium, with our DICE layer as an Application RoT partition, in place
of a secure monitor of our own (ruling 935's option (a)). Owner, verbatim:
"the TrustZone-M secure world is built on Trusted Firmware-M with our DICE
layer on top, not a secure monitor written from scratch." Ruling 935's other
points stand: no vendor secure world, no PSA token (TF-M without its Initial
Attestation partition, or with it not exposed). Refs #590.

## TF-M v2.3.1 platform ports

The pin is `scripts/tfm-measure.sh`'s: tag TF-Mv2.3.1, commit 0b40d780.
Found from that commit's `platform/ext/target` tree (shallow fetch, out of
tree) on 2026-11-20.

| board          | TF-M v2.3.1 port                                         |
|----------------|----------------------------------------------------------|
| STM32H573I-DK  | yes: `stm/stm32h573i_dk` (on `stm/common/stm32h5xx`)     |
| NUCLEO-H563ZI  | no board port; `stm/common/stm32h5xx` is the family base  |
| nRF54L15       | yes: `nordic_nrf/nrf54l15dk_nrf54l15_cpuapp`              |
| mps2-an505     | no: `arm/mps2` has `an519` and `an521` only               |

Settled for slice 2 (coordinator):

1. The QEMU target is TF-M's upstream `arm/mps2/an521`, run as
   `qemu-system-arm -M mps2-an521`; no AN505 port of our own. The mps2-an505
   targets and `src/hal/cortex-m/tz/` stay as they are; slice 3 replaces the
   monitor.
2. The NUCLEO-H563ZI gets a board port derived from `stm/stm32h573i_dk` in
   slice 4 (the H563 has no SAES or PKA, so its crypto config differs).

## Slices, with their tests

1. This plan; ADR #15 and the MCU DICE ADR amended to (b1). Docs only.
2. TF-M built out of tree (`scripts/tfm-build.sh`, the pins shared with
   `scripts/tfm-measure.sh`) for an521 and the STM32H573I-DK: Profile Medium,
   BL2 on, Initial Attestation off, tf-m-extras' example non-secure app.
   Tests: `make tfm-qemu-test` (test/integration/cortex-m/qemu_tfm_test.sh)
   boots bl2, tfm_s and ns on mps2-an521 to "Booting TF-M" and the NS app's
   first line; `make tfm-image TFM_BOARD=stm32h573i-dk` builds the signed
   images. Status: code done, gates run in coordinator verify (the lane
   image has no Arm toolchain or QEMU). The verify records the image sizes
   (`$TFM_WORK/out/<board>/sizes.txt`) for both boards here.
3. The DICE layer as an Application RoT partition (CDI, DeviceID key, alias
   key) with a PSA client API for the non-secure side. Tests: host unit tests
   of the partition logic; the QEMU integration target calls it and checks
   the alias certificate against go-xkms device-attest-01's dice format.
   Status: partition core done and host-tested (`src/tz/dice_partition.c`
   dispatch and start, `src/tz/tz_s_client.c` NS client over `psa_call`,
   `test_dice_partition`); manifests in `src/tz/tfm/`. Remaining: the
   partition's CMakeLists.txt and SFN glue (`tfw_dice_partition.c`: UDS by
   HKDF-SHA256 from `TFM_BUILTIN_KEY_ID_HUK`, info "tfw-dice-uds-v1";
   measurement = Measured Boot slot 3 (RT_1, the NS image), refused unless
   locked), the `scripts/tfm-build.sh` flags (TFM_EXTRA_MANIFEST_LIST_FILES,
   TFM_EXTRA_PARTITION_PATHS, TFM_PARTITION_TFW_DICE, the Measured Boot set:
   TFM_PARTITION_MEASURED_BOOT, CONFIG_TFM_BOOT_STORE_MEASUREMENTS,
   MCUBOOT_DATA_SHARING), the NS app call and the QEMU check, a changelog
   fragment.

Decided in slice 3 (r109, for the coordinator to confirm): the UEID is
HMAC-SHA256(UDS, "tfw-dice-ueid-v1") cut to 16 bytes; the service SID is
0xD1CE0000, stateless; the partition answers a `tfw_status_t` as the
`psa_call` status; enabling tf-m-extras' Measured Boot partition goes beyond
slice 2's partition set.
4. The NUCLEO-H563ZI and nRF54L15 builds, and the hardware run on the
   STM32H573I-DK (probe-dependent), with the board pages updated.

Slices 2-4 follow issue #608; the issue text could not be read from this
lane, so their order is the coordinator's to confirm.

## Out of scope

The ESP32-P4 (ruling 1024 (b), row #606), the AVR path, the `stm32h5` SPEC
row wording (its own SPEC change), CI workflow changes, option bytes, TZEN,
RDP and lock bits.
