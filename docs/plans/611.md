# #611: ci.yml to ci-template v1.48 (PR #613)

## Codex round 1 P1s (ruling 901, ruling 997)

- [x] **The docs-only path checks images it never builds.** The image job's
  `Check the images carry no private address` step passed the esp32 and
  integration images to `scripts/ci-image-history.sh` on a docs-only PR,
  which builds only the toolchain image; the script exits 1 on an image it
  cannot inspect, so docs-only PRs on a self-hosted runner failed. Fix: the
  step reads `DOCS_ONLY` from `needs.preflight.outputs.docs_only` and checks
  the toolchain image alone on the docs-only path (CUSTOMIZE, DS-3166).
- [x] **Cold integration builds bypass the image-history check.** The
  integration and soak jobs leased only an integration image already on the
  daemon; on a cold daemon `IT_LEASE_ID` stayed empty, the check skipped, and
  `make integration-test` built and ran the image unchecked. Fix: both jobs
  log in to the registry and run `make docker-build-it` (`Build the
  integration image`) before the lease; the lease fails (`::error::`) when the
  image or the lease container is missing; the check's `if:` no longer skips
  on an empty `IT_LEASE_ID`; the run steps re-tag the checked id, so
  `docker-build-it` there reuses it and nothing builds after the check.

Regression test: `scripts/test_ci_image_history_steps.py`.

## scripts-test red on the preflight schedule guard

- [x] The v1.48 merge added the dispatch-ref and `lane-ckpt/` refusals to
  the schedule-guard step, which read `$REF` and `$HEAD_REF` under `set -u`;
  `scripts/test_schedule_guard.py` runs the step without them (as on v1.34)
  and failed with `unbound variable`. Fix: the refusals read `${REF:-}` and
  `${HEAD_REF:-}` and the dispatch refusal applies when REF is set, which the
  step's env always does (`github.ref`, never empty on a dispatch); the
  checkpoint check is a `[[ … == lane-ckpt/* ]]` match.

## Codex round 2 (ruling 997)

- [x] **P1: FIPS setup-go finds no go.sum.** setup-go caches by default and
  looks for a root `go.sum`, which this repository lacks, so the nightly fips
  job failed at setup. Fix: its setup-go step names `xkms/go.sum` and
  `sdk/go/go.sum` as `cache-dependency-path`.
- [x] **P1: a refused checkpoint PR could pass CI Gate.** A `lane-ckpt/*` PR
  touching only docs got `verdict=refused`, but image and lint-gates read the
  verdict on schedules only and CI Gate accepted the docs-only skips. Fix:
  image, lint-gates and integration start only on `verdict == 'run'` on every
  event, and CI Gate fails on `refused` on every event.
- [x] **P2: `proof()` was never called.** No path set `verdict=proven`, so the
  tree reuse it documented never ran. Fix: removed `proof()`, the `get()`
  helper only it used, the `proof` output, the guard's `SHA` and `REPO_API`
  env, and the comments claiming tree reuse; every main push runs the full
  tier.

Regression test: `scripts/test_ci_verdict.py`.

## Codex round 3 (ruling 997)

- [x] **P1: an unknown `||` operand was dropped.** The runner-label check
  evaluated `U || 'ubuntu-latest'` to the right operand, but GitHub returns a
  truthy left operand, so `runs-on: ${{ vars.CI_RUNNER || 'ubuntu-latest' }}`
  passed as hosted and, naming no literal `release`, escaped the release
  rules. Fix: an unknown left operand makes the result unknown, so such a
  runs-on is refused under (c); with a `# self-hosted:` waiver it is checked
  as a possible `release` job, its `if:` restricted like one.
- [x] **P1: a failed vulnerability gate skipped the misconfiguration scans.**
  Both nightly misconfiguration steps had no status function, so the implicit
  `success()` skipped them whenever the Trivy gate failed. Fix: their `if:`
  starts with `!cancelled()` and requires its own scanner step
  (`trivy_version` on GitHub, `install_trivy` on Gitea) to have succeeded;
  the gate steps are unchanged, so the job still fails on a finding.

Regression test: `scripts/test_ci_runner_expr.py`.

## ci-template v1.49

- [x] **v1.49 adopted (ruling 1051, handbook #83).** On github.com preflight
  runs on the Dells' bigdisk pool, `fromJSON(vars.CI_PREFLIGHT_RUNS_ON ||
  '["self-hosted","linux","x64","bigdisk"]')`; Fleet Ops sets the variable to
  `"ubuntu-latest"` while the Dells are down. The schedule guard's AGENT_TOKEN
  is passed off github.com only. `Runner labels (ruling 633)` checks
  preflight's runs-on, and only that job's, with the variable unset (exactly
  [self-hosted, linux, x64, bigdisk] passes too) and set (a standard image);
  any other job reading the variable still reads an unknown.

Regression test: `scripts/test_ci_runner_expr.py` (class `PreflightRunsOn`).

## Codex round 4 (ruling 997)

- [x] **P1: an evaluated `release` label passed under a waiver.** A runs-on
  such as `${{ format('{0}{1}', 're', 'lease') }}` with a `# self-hosted:
  hardware:` waiver names no literal `release` and evaluates without an
  unknown, so the waiver skipped the release rules. Fix: a waived runs-on is
  checked as a possible `release` job when its value is unknown on some event
  or any evaluated label names `release`.
- [x] **P1: Integration and Soak shared a temporary image tag.** Both build
  the integration image on the shared Docker pools on a schedule or dispatch
  run, and both left IMAGE_BUILD_ID at docker.mk's `build`, so one could
  remove `<IT_IMAGE>-build` before the other tagged it. Fix: each sets
  IMAGE_BUILD_ID to run id, attempt and job; docker.mk's tag to IT_IMAGE stays
  the one write of the shared name.

Regression tests: `scripts/test_ci_runner_expr.py`,
`scripts/test_ci_image_build_id.py`.
