## Owner question (blocks slice 2)

The ESP32 application has no route to the image key. The key's one home is
layer 0: `mk/arch/esp32-targets.mk` generates `p256_key_slot.c` from
`ESP_IMAGE_KEY` into the bootloader component only, and the platform block
the application can read holds the key's SHA-256 pin, not the key. Nothing
under `src/` links `tfw_boot_p256_key`, `tfw_boot_verify` or a P-256
verifier on the ESP32. Each way to verify needs a ruling:

- (a) A second home: link the generated key slot (and `verify_p256_soft.c`,
  or the ROM verifier on the P4) into the application image, checked
  against the platform block's pin as `boot/hal/esp32/l0_gate.c` does. The
  application partition then carries the image key; touches
  `mk/arch/esp32-targets.mk`, outside this lane.
- (b) Layer 0 verifies: `OTA_CONFIRM` writes the signature to a record for
  layer 0, as `OTA_ACTIVATE`'s authorization goes to `tfw_auth` today, and
  layer 0 marks the image valid at the next boot. A new record and a change
  to who calls ESP-IDF's confirm: an ADR change
  (`docs/multi-arch/esp32-p4-design.md` section 2.3).
- (c) Layer 0 hands the key to the application through the handoff block:
  a new handoff field, a wire-level change to that block.

Until then the failing test stands at the branch tip.
