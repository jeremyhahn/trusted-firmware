# #620: OTA_CONFIRM's request reaches flash for tfw-boot on the MCXN947

Row `mcxn947` follow-up (ruling 1052, DS-9745).

## Objective

`src/hal/cortex-m/mcxn94x/hal_eeprom.c` takes OTA_CONFIRM's request
(`TFW_BOOT_CONFIRM_ADDR`, `TFW_BOOT_CONFIRM_LEN`) with a plain `memcpy` into
the platform window. On the board that window is flash: the store programs
nothing, and tfw-boot's `tfw_boot_nvm_read` never sees the confirm. The
request goes instead through tfw-boot's ROM flash helper
(`tfw_mcxn_flash_update`, boot/hal/cortex-m/mcxn94x/mcxn_flash.c) into the
platform sector, a read-modify-write that keeps the platform block's other
bytes: the fix rp2350 got in #495/#500.

## Slices

1. Test (`test/unit/test_mcxn94x_eeprom.c`): the case that asserted the
   store path is replaced by one that writes the confirm request over a
   patterned platform sector and checks that it reads back from the ROM
   flash model's platform sector, that one platform erase ran, that every
   other byte of the sector is unchanged and the user sector untouched.
   The test's `TFW_MCXN_EE_WINDOW` alias to model memory, which made the
   store look as if it reached flash, points at a scratch buffer instead.
   Fails on the memcpy.
2. Fix: the write calls `tfw_mcxn_flash_update` on
   `TFW_CM_PLATFORM_BASE + addr` with the platform sector's end as the
   flash end, under the same interrupt mask as the user sector's write.
   `TFW_MCXN_EE_WINDOW` goes from the file and the test. The helper takes
   its end bound as an argument, so mcxn_flash.c does not change. The
   mutation (the memcpy back) fails the new case: no platform erase.
3. Docs: board page item 8 marked done, this plan, the changelog fragment.

## Out of scope

- Hardware: host-tested against the ROM flash model only; no board flashed.
- tfw-boot's own handling of the request (boot/), unchanged.
- Any other mcxn947 follow-up on the board page.
